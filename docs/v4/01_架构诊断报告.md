# 01 · 知命明镜台 Core v3 架构诊断报告

> 作者：Claude（项目"大脑"）　日期：2026-10-17（Asia/Shanghai）
> 诊断对象：线上部署等价源码 `work/release`（tree `9e938dd6…`，与 GitHub `789037f` 一致；GitHub main 之后只多了 CI 测试配置修复与交接文档两个提交）。
> 方法：三路代码勘察（Agent 层 / 记忆与时间 / 前端）+ 一次架构评审 + 外部资料调研。所有结论均附 `文件:行号`，路径相对仓库根目录。
> 本文只陈述事实与判断，不包含任何密钥、出生资料或私人对话正文。

---

## 0. 一句话结论

**Core v3 在"数据安全、幂等、可恢复"上做得很扎实，但在"像一个懂你的助手"上几乎是反方向设计：** 它是一条固定的十段流水线，模型看不到自己说过的话、几乎不被允许记住你、只知道一个光秃秃的日期，还有一个 134 条正则组成的校验器会把整轮回答直接吞掉。前端则是一个 181KB 的单文件，三套样式互相打架。

**处方：保留地基，重建大脑与门面（Core v4）。**

---

## 1. 用户的四个抱怨 → 根因对照表

| 用户感受 | 直接根因（证据） |
| --- | --- |
| "它忘事" | ①模型从来看不到**自己**之前的回答；②绝大多数生活信息被判为"敏感"而不保存且无确认入口；③旧记忆在迁移时被卡死；④新会话/换渠道=上下文清零；⑤没有检索、没有摘要 |
| "看不懂时间、不知道放没放假" | 只把 `YYYY-MM-DD` 字符串给了第一个阶段；没有星期、时刻、农历、节气、节假日、调休；历史消息没有时间戳 |
| "Agent 适配极差、不主动" | 不是 Agent：固定十段流水线，模型不能选择工具、不能循环、不能停下来问；唯一的"提问"只在缺出生资料时附在答案末尾 |
| "前端审美很差、体验差" | 三层样式冲突、大量 8–11px 小字和低对比度、无字体、无暗色、每页 100px+ 装饰标题、假打字光标（实际 1 秒轮询数据库）、依据面板永远显示 0 |

## 2. 证据详述

### 2.1 不是 Agent，是流水线

- `mingjing_core/runtime/graph.py:15` 定义 `PHASES = ("intake","memory","snapshot","plan","calculation","specialists","synthesis","review","validation","commit")`，`graph.py:47-52` 把它们用 `add_edge` 线性串起来。LangGraph 在这里只是"带存档点的列表"。
- 每次模型调用 = **一条** user 消息，内容是 `json.dumps(payload)`（`adapters/model.py:21-27`）；唯一的工具 `submit` 用来交结构化结果（`model.py:28-29`）。模型无法自己决定"再查一下记忆""再算一个日期""先问问用户"。
- `adapters/model.py:1` 的文档字符串直接写着 *without tool orchestration*。讽刺的是被退役的旧 `hermes/chat_agent.py:14-27,104` 反而有一个 8 轮的真工具循环（`search_records / read_record / calculate_charts / remember_fact`）。
- 计划阶段 `consultation.py:408-439` 不调用模型，而是用正则改写模型的计划（例如 `consultation.py:417` 只要出现"不要…八字"就清空所有体系，`:420` 出现"怎么选/辞职"就强制决策模式）。

### 2.2 忘事的五个原因

1. **模型看不到自己的回答。** 用户消息存成 `message` 实体（`consultation.py:314-317`），助手回答只存在 `core_runs.result`（`consultation.py:1002-1030`）。`MemoryService.snapshot()` 的历史只取 `message`（`application/memory.py:382-384`）。`/api/history` 在展示时把答案拼回去（`adapters/web.py:486`），所以**你在页面上看得到连续对话，模型却看不到**。"那第二个方案呢？"它无从接续。
2. **记忆写入闸门把日常信息挡在门外。** `memory.py:199-200`：
   `sensitive = subject!='self' or kind not in ('preference','constraint') or bool(field) or SENSITIVE.search(quote)`
   → 背景、目标、事件、担忧**全部**算敏感 → `pending_confirmation`。而前端只处理 `saved` 回执（`static/app.js:288`），pending 被静默丢弃，且**没有任何确认接口**。"我下周三面试""在准备考研""和老板吵架了"几乎都记不住。
3. **正则误伤。**
   - `memory.py:11` 的拒绝保存正则会把"别忘了记住我不吃辣"当成"不要记住"。
   - `memory.py:191-192` 的假设句检测以整句为窗口，"你觉得呢？我不能上夜班"被判成假设。
   - `memory.py:196` 第三人称检测会被"其他的""我和他是同学"误触。
   - `memory.py:12,125-133` 授权词必须出现在事实**之前**，"我下周三面试，请记住"不生效。
4. **"以前记得、现在不记得"的直接原因：** 迁移时旧系统的背景/目标/事件记忆走了同一个闸门，被存为 `legacy_unverified + pending`（`migration_core.py:228-245`）；`memory.py:331` 的 `facts()` 只取 `granted` 且非 `legacy_unverified`；而 `correct_fact` 要求 `granted`（`memory.py:241`）→ **这些记忆永远无法被恢复**。没有原话锚点的旧记录变成 `legacy` 实体（`migration_core.py:243-245`），永不进入上下文。
5. **上下文窗口极窄、没有检索。**
   - intake 只给约 12 条历史（含本条），每条截断 1000 字（`consultation.py:344`）；synthesis 给 16 条、截断 1600 字（`:510`）。**全部只有用户发言、没有时间戳**，还被系统提示定性为"不可信资料"（`consultation.py:28`）。
   - 事实排序 `selected_facts`（`consultation.py:46-52`）用 `[一-鿿]{2,8}` 贪婪切出 8 字长串，几乎匹配不到任何事实 → 实际只是"约束/偏好优先 + 存储顺序"。
   - 没有摘要、没有情景记忆：`Episode` 契约定义在 `domain/contracts.py:80-89`，**全仓库没有任何代码生成它**。
   - 会话隔离：新会话按钮（`app.js:380-385`）= 模型历史清零；飞书是独立会话 `feishu:p2p:<chat_id>`（`adapters/feishu_gateway.py:70`）；报告是 `report:<id>`；网页上的事项/塔罗/记忆操作落在 `'default'`（`memory.py:57`）。
   - 事项只传 ID：事项标题、目标、事件从未进入模型（`consultation.py:340`）。
   - 潜在 bug：`repositories/postgres.py:174` 按 `created_at` 升序 `LIMIT 10000`，超过一万条后**最新**消息反而取不到。

### 2.3 不懂时间

- `consultation.py:26,42-43`：`SHANGHAI=timezone(timedelta(hours=8))`，`today()` 只返回日期字符串，**只放进 intake 的 payload**（`:341`）。synthesis/review/specialists 都看不到今天。
- 没有：几点、上午/下午、星期几、农历、节气、干支、节假日、调休、"距离上次聊天多久"。历史消息的 `at` 字段存了却在拼 payload 时被丢掉（`:344,:510`）。
- `target_date` 由模型凭一个光秃秃的 ISO 日期去推"下周三"（`consultation.py:433-438`），`time_scale` 只有 natal/daily/monthly/yearly，周报、季报没有对应口径（`domain/consultation.py:17`）。
- 报告只把日期写在句子里"请生成{day}的晨报"，`selection` 不带 `date`（`adapters/channels/reports.py:62-71`）。
- 讽刺的是，项目里已经有现成的轮子：排盘隔离环境里的 `lunar-python 1.4.8`（`requirements-charts.lock:17`）自带 `HolidayUtil`，**已经内置 2026 年全部法定假日与调休**（经核对与国务院 2025-11-04 通知一致），还有农历、节气、干支、黄历宜忌。只是从没接进对话。

### 2.4 校验器：134 条正则会把整轮回答吞掉

- `consultation.py:527-926`，约 400 行、38KB，占文件 46%，**134 次正则调用**、13 类问题。
- 大量规则是对某几次具体对话的"补丁"，例如 `re.fullmatch(r'(?:今天)?向A发出班次与', start)`（`:706-713`）、整句白名单 `'若B费用不可接受能否无损失退出，取决于B的退出条件，待核实'`（`:794-811`）。
- 因为它读不懂否定句，系统提示被迫写"即使否定也不许出现'已保存'等字样"（`consultation.py:34`）。
- 失败处理（`:928-939`）：最多修一次，仍有问题就抛 `InvalidAnswer`，图节点把错误换成"本轮阶段未完成（validation）"（`runtime/graph.py:42-44`）→ **用户一个字的回答都拿不到**。
- 69 个 `tests/test_core_*.py` 里有 29 个是这类否定句回归（文件名带 4288、5908、8A7 等运行号）。最近的提交几乎都是"处理某种否定句式"。这是一个**只会越补越多的结构**。
- 预算 `CALL_LIMITS={'fast':2,'standard':6,'deep':10}`（`repositories/postgres.py:23`），失败的调用也计数；fast 模式根本没有修复机会，任何一条正则命中即失败。

### 2.5 模型绑死、不可移植

- 只有 Anthropic 线协议：`{KIMI_BASE_URL}/messages` + `x-api-key` + `anthropic-version`（`adapters/model.py:20,35`）；`thinking.budget_tokens=1024`、`temperature=1`、`max_tokens` 写死（`:29-31`）；无重试、无流式、240 秒超时。
- `from_base()` 永远构造 `ConfiguredModel`（`consultation.py:61,84`），没有供应商开关。
- 输出 schema 是 Pydantic 原生 `model_json_schema()` 加运行时补丁（`consultation.py:168-194`），含 `$defs/$ref/anyOf/Any`，OpenAI 严格函数调用、部分国产模型都会拒绝。
- 好消息：`ModelPort` 接口本身很窄（`domain/consultation.py:81-82`），换掉实现不难。

### 2.6 没有主动性、没有"人"

- 唯一的主动行为是四种定时报告。`FinalAnswer.follow_up` 只是印在答案里的一句"何时回看"，没有任何程序会在那个时间点真的来找你（`domain/consultation.py:67,151`）。
- 没有人格设定：系统提示第一句是"你为知命明镜台提供本阶段结构化结果。只调用submit一次。"（`consultation.py:27`）。
- 没有用户画像：profile 只有出生资料+姓名+性别（`domain/consultation.py:23-28`）。旧 Hermes 曾经每轮注入 `profile / continuity / calibration`（`hermes/chat_agent.py:46-48`），v3 丢了。
- 知识包只有 16 条规则（八字 6、紫微 5、西占 3、塔罗 2），超出范围一律 `RULE_GAP`。模型主要在"复述模板句"。

### 2.7 前端

- `static/app.js` 181KB / 2174 行，单行常超 1000 字符；92 处 `innerHTML` 字符串拼接、64 处生成式内联 `onclick`；全局变量当状态。
- 样式三层打架：深色星空 `base.css` + 用 60 个 `!important` 覆盖成浅色的 `paper.css` + Tailwind 预检。深色残留颜色漏进浅色主题，例如紫微星曜 `#D8DCE8` 画在 `#fffdf8` 上（对比度约 1.3:1，`app.js:889`）。
- 字号：`paper.css` 里 8px×3、9px×4、10px×37、11px×48 处；没有任何 `@font-face`，Windows 上标题回退到宋体。
- 每页顶部 100–130px 的"THE MIRROR / 诗意大标题"，手机首屏三分之一被装饰占据。
- 没有真流式：服务端 SSE 每秒查一次数据库，只发阶段名（`adapters/web.py:170-181`），前端却放一个闪烁的打字光标。
- "本轮依据"面板读取后端早已不发的字段，永远显示"已接入 0 条"（`app.js:140-146` vs `web.py:167,175`）。
- 旧"六维应验率/准不准"页面与"反思而非预言"的定位冲突；pending 记忆在 App 里没有确认按钮（`app.js:2106`）。
- 无 CSP；token 放 `localStorage`。

## 4. 重写还是重构？

| 方案 | 结论 |
| --- | --- |
| 在 v3 上继续打补丁 | ✗ 结构性问题（流水线、单消息、拒绝式记忆、正则校验）无法靠补丁解决，只会让校验器和测试继续膨胀 |
| 全部推倒重写 | ✗ 数据库、排盘、塔罗、投递是验证过的资产；重写它们浪费工期并危及真实数据 |
| **保留地基、重建大脑与门面** | ✓ 运行时、上下文、记忆策略、模型层、校验、流式、命理能力、前端、飞书交互重写；地基原样复用并按需扩展 |

这就是 Core v4。具体设计见 `02_v4架构蓝图.md`。

## 5. 主要风险

| 风险 | 缓解 |
| --- | --- |
| 放开记忆后误记、记错 | 每次写入都有可见回执和一键撤销；敏感类先问；纯推断标记为"推测"永不当事实；"关于我"页可全量审阅 |
| Agent 循环失控（死循环、乱调工具） | 迭代上限、墙钟上限、同参数重复熔断；工具按情境暴露；所有副作用幂等 |
| 去掉正则校验后说过头 | 硬约束下沉到工具（盘面只能来自计算、保存只认回执、塔罗不可换牌）；不同家族模型做评审员；危机模式保留 |
| 迁移不可逆 | 只前进迁移；每阶段切换前完整备份；先 stage 后生产；每阶段有回滚点 |
| 国产模型工具调用行为不一致 | 能力探测脚本 + 能力矩阵 + 降级链；评测集在多个模型上跑分 |
| 飞书权限与发布审批 | 列入用户待办（见 `00_先读我`） |
