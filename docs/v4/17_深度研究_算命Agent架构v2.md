## 0. 结论先说

### 0.1 最重要的五个发现

1. **时辰校正：用"命理吻合度"反推出生时刻，独立实证接近随机。** 2026 年一项预注册的计算研究用 63 位有出生证明级数据的人物、888 个有日期的事件做留一交叉验证：主限、小限、法达等所有定时技术定位出生时刻都在随机水平，只有"白天还是夜里出生"能分到约 70%【证据】。v4 现在的 U9 设计（合成人物评测 + 输出前三名）会交付一个"看起来很准、其实不能区分"的功能。合成人物的事件是用同一套规则生成的，拿来评测是循环论证。真正能算准、又常被忽略的是**可计算的不确定性**：中国 1986–1991 年夏令时、真太阳时（经度修正 + 均时差）、时辰交界、晚子时口径、节界。→ U17–U21。
2. **Kimi 会员端点：风险不只是额度用完。** 官方社区准则写明订阅"仅供个人交互式使用"，"不要把 Kimi Code 用于非交互式自动化"，举的例子就是**脚本批量运行**；违规会被限制并发【证据】。错误参考列出了 4 种 403：5 小时额度、周额度、**月额度**（账号冻结，Kimi 全部会员权益一起停）、**并发风控**（和额度无关）【证据】。其他坑：关闭思考后 K3 请求会**静默改由 K2.8 Preview 处理**；"指定某个工具"的 `tool_choice` 与思考不兼容；多轮工具调用必须原样回传完整助手消息【证据】。仓库现状有三处要修：`reasoning_replay: false`；会员端点的 429 被一律当成额度用完；思考仍用 v3 遗留的 `budget_tokens: 1024`。→ U37–U43。
3. **命理推理：增益来自"规则函数化 + 工具计算 + 单体系子 Agent + 置信度合参"，不来自多轮辩论。** 在比赛题上，通用模型接近随机：MingLi-Bench 2025 子集上 Kimi K2.5 只有 27.5%（随机 25%），最强通用模型 37.5%；带 200 多个工具的专业 Agent 达到 45%，截尾计 50%；人类前 20 名平均 51.9%【证据/二手】。BaziQA 上最好的模型是 36.7%【证据】。另一边，"辩论还是投票"研究证明多 Agent 辩论的收益大多来自投票本身，辩论过程在数学上是鞅，不提高期望正确率【证据】。→ U12–U16。
4. **长期记忆：最弱的一环是"信息更新/冲突消解"和时间推理。** MemoryAgentBench 上所有记忆系统的多跳冲突题准确率都 ≤7%，商用记忆层单跳也只有 7–18%【证据】。有效做法都有实测增益：按"轮"切分、用事实扩展检索键、按时间范围过滤检索、"先做笔记再回答"的读法、日期运算交给代码（29.8%→77.7%）【证据】。此外，抽取式记忆会丢掉"助手自己说过的话"（Zep 在这类题上从 94.6% 降到 80.4%）【证据】。→ U22–U26。
5. **评审：同模型评审最危险的地方，是它在自己出错时袒护自己。** 研究显示，评审模型自己作为生成者出错时，最容易偏爱自己的错误答案，而且模型越强越明显。评审前先做长链推理能明显减轻这个问题【证据】。另外，20 条校准样本在统计上证明不了 80%：16/20 一致的 95% 置信区间约为 58%–92%【可计算】。记忆评测的审计还发现，评审会放过 62.8% 故意写错的答案【证据】。→ U32–U36。

> 附带发现（法规）：网信办等五部门的《人工智能拟人化互动服务管理暂行办法》已于 2026-04-10 公布，2026-07-15 施行。它禁止"过度迎合用户、诱导情感依赖或者沉迷"，要求每连续使用 2 小时提醒一次，并且不得阻碍用户退出【证据】。它只适用于"向境内公众提供"的服务，明镜台只给本人用，所以不直接适用；但其中的条款很适合当设计底线，→ U29–U31。

## 1. 方向一：命理推理的 Agent 架构

### 1.1 发现

**(a) 比赛题基准：通用模型略高于随机，专业 Agent 接近人类高手均值**

| 来源 | 设置 | 关键数字 |
| --- | --- | --- |
| BaziQA-Benchmark（arXiv 2602.12889，2026-02）【证据】 | 200 道四选一题，来自 2021–2025 年全球命理师大赛；每年 8 位命主 × 5 题；程序排盘后渲染成固定模板，一次会话里连续作答 5 题 | 最好 DeepSeek-Chat-V3 36.7%（95% CI 33.2–40.2），DeepSeek-R1 34.1%，GPT-5.1-Chat 32.5%，Gemini-3-Pro 32.1%；各模型置信区间大量重叠，排名只是描述性的 |
| 同上：结构化推理协议 SRP【证据】 | 固定三步推理顺序：①定量扫描（五行、日主强弱、全局结构）→ ②按当下时间语境给交互关系定严重度并排序 → ③按严重度把信号映射到事件 | 效果不稳定：2025 子集上同一领域有 +30 个百分点，也有 −20 个百分点。作者结论是"推理顺序敏感"，失败集中在**精确时间定位**和**多条件同时满足** |
| MingLi-Bench（DestinyLinker，MIT 协议，160 题，八字 + 紫微，2022–2025）【证据】 | 盘由 iztro 预排后注入；排行榜只用 2025 年 40 题（8 个案例）以降低模型背过题的可能；每题跑 5 轮，≥3 轮答对才算对；按比赛规则用截尾平均 | 人类前 20 名平均 51.9%（截尾 53.5%）；Tianfu Agent 45.0%（截尾 50.0%）；Claude Opus 4.6 37.5%；Gemini 3.1 Pro 37.5%；GPT-5.4 32.5%；DeepSeek V3.2 30.0%；**Kimi K2.5 27.5%**；随机 25% |
| BaZi-LLM 人物模拟（arXiv 2510.23337，WordPlay 2025）【证据】 | 50 位名人、488 道题；对比"裸模型 + 盘""加规则知识""完整系统" | 只加规则知识：DeepSeek-V3 39.3→35.9，GPT-5-mini 34.0→36.9，有升有降；完整系统 51.2 / 47.1 / 55.3。**打乱生日后，完整系统下降 20.7%–45.7%，裸模型几乎不变（+8.1% / −0.2% / +2.4%）**，说明裸模型根本没在用盘。案例中，同一张盘不同模型分别判成伤官格和从儿格 |

注意三点：
- 这些分数衡量的是**与职业命理师给定答案的一致性**，不是现实预测的效度（16 号报告已强调）【证据】。
- 40 题的统计噪声很大：在 40% 左右的正确率上，40 道题的标准误约 7.7 个百分点，95% 置信区间约 ±15 个百分点【可计算】。
- 2025 年比赛题有可能进入 2026 年发布模型（例如 K3，2026-07 发布）的训练数据【推测】。

**(b) Tianfu Agent 的结构：目前公开信息里离"人类均值"最近的设计**【二手：新智元/36氪、投资界 2026-05-25 报道其技术报告】

- **200 多个原子工具，分四级可见**：自动注入型（十神、宫位）、按需调用型（生克、飞宫）、转译调用型、只对特定子 Agent 开放的触发注入型。不同推理阶段、不同子 Agent 看到的工具集不同，以减少选择混乱。
- **三大流派的规则函数库**：每条规则封装成带元数据的函数，元数据包括适用场景、时间跨度、事件类型、优先级，由人类专家预先标注。**条件满足时才把结论注入上下文**。仅子平一派的规则就超过一百条。
- **每个子 Agent 只在单一体系内推理**，维护自己的工具和上下文。
- **三层置信度**：工具层由算法给出非确定判断（强弱、多象吉凶）的置信度；子 Agent 层由模型自评各观点的显著性；多流派合参层用人工经验置信度加权调和冲突。团队自己也承认，这替代不了自动验证。

**(c) 多 Agent：投票有效，辩论本身无效**

- "Debate or Vote"（arXiv 2508.17536，NeurIPS 2025）【证据】：在 7 个基准上，多 Agent 辩论的大部分收益可以由多数投票单独解释。论文证明辩论过程中各 Agent 信念的演化是一个鞅，即辩论本身不提高期望正确率；只有让更新偏向"纠错"才有帮助。
- Smit et al.（ICML 2024）与后续系统评测（arXiv 2502.08788）【证据】：辩论方法常常赢不过单 Agent 或自一致性；在相同调用预算下，差距更明显。
- Huang et al.（ICLR 2024）【证据】：没有外部反馈的"自我纠错"常常让推理变差。
- Anthropic 多 Agent 研究系统【证据】：多 Agent 系统约消耗聊天的 15 倍 token，适合可以并行拆开的广度任务。

**(d) 日期运算交给代码，提升巨大**

- TReMu（arXiv 2502.01630）【证据】：多会话时间推理题上，GPT-4o 直接回答 29.83%，思维链 61.67%，让模型生成 Python 做日期运算后 77.67%。这与"程序做事实"的原则一致，也是 U2 时间交互表的直接依据。

### 1.3 建议的架构调整

- **U12 规则命中层（高）**：在 `chart_compute` 的产物里新增 `rule_hits[]`，或单独做一个只读工具 `chart_rules(system, scope)`。每条命中：`{rule_id, school, name, condition_met, evidence_paths[], priority, domains[], time_scale, source{book, chapter}, claim_kind:"traditional"}`。
  - **程序只判断条件是否成立**【可计算】，例如"月令为官、年干透伤官"。条件成立意味着什么，写在技能包对应章节里，并标注流派与出处【传统说法】。
  - 第一批只做八字，40 条以内（格局成败条件、常见十神组合、调候缺失、刑冲合害落宫），每条都要有正例盘和反例盘测试。
  - 规则表里的优先级是【项目口径】，按流派分别给，不合并成一个"真理"。
- **U13 专科推理协议与证据账本（高）**：`specialist.md` 改为固定的四步，每一步只能引用 `〔c#〕` 和 `〔r#〕`（规则命中）：
  ①结构扫描；②按程序给的优先级处理时间层交互；③映射到所问领域；④列出反证与不确定。
  输出改为 JSON：`{claims:[{text, refs[], school, direction:"+"|"-"|"mixed", confidence:1-3}], gaps[]}`。BaziQA 显示固定顺序的收益不稳定，所以这一协议必须能在 E2 里开关，用 A/B 实测决定是否默认开启【推测】。
- **U14 结构化合参，不做辩论（高）**：
  - 各专科独立运行，互不看对方结果。
  - 综合者按确定性规则组织：多个体系同向的，说"几个体系都指向"；冲突的，并列说明。
  - 离散判断（格局候选、旺衰类别、比赛选择题）用 k 次独立采样后多数投票，**只在"生成命理档案"和"评测"时使用**；日常对话不用，以节省额度。
  - 不实现多轮辩论。
- **U15 命理档案的自一致性生成（中）**：U3 首次生成档案时，对每项核心判断独立推理 k=3 次（项目口径）。
  - 3/3 一致：标"稳定"。
  - 2/3 一致：标"倾向"。
  - 三次都不同：标"存疑"，并列给出各个可能。
  - 档案记录每项的一致度与依据别名。之后的解读默认与档案一致（U3 不变）。
- **U16 E2 评测重设计（中）**：
  - 配置：C0 裸模型不给盘；C1 裸模型 + 盘；C2 v4 单 Agent；C3 C2 + 规则命中层；C4 深度模式（专科 + 合参）。
  - 安慰剂对照：题目不变，换成别人的盘。
  - 报告：准确率、95% CI，以及同一批题目上**配置之间的配对差**（Miller 2024 的方法，见 §5）。
  - 额度：全量（360 题 × 5 配置）只在开放平台上跑；会员端点只跑 2025 子集（MingLi 40 题 + BaziQA 40 题），每题 1 轮，3 种配置（C1/C2/C3），约 240 次调用，分 3 个以上 5 小时窗口（需用户决定，§9）。
  - 报告头必须写明：测的是与命理师答案的一致性，不是预测效度；题目可能已进入训练数据。

## 2. 方向二：时辰校正（用户已定为必做）

### 2.1 发现

**(a) 传统"定时辰"方法**【传统说法】（来源多为命理博客与转帖，**没有找到可靠的古籍原文出处**，以下按"民间流传口诀"处理）

| 方法 | 内容 | 问题 |
| --- | --- | --- |
| 三组时辰分法 | 把十二时辰分为子午卯酉、寅申巳亥、辰戌丑未三组，再用发旋位置/数量、婴儿睡姿、面型、小指长短、走路姿势等对应到组 | 各家说法互相矛盾，例如发旋偏左还是偏右，两种口诀方向相反；最多只能缩小到 4 个时辰一组 |
| 六亲口诀 | 兄弟人数（含夭折）："子午卯酉兄弟多，寅申巳亥两三位，辰戌丑未独一个"；"胎次"按父母怀孕胎次（含流产）而不是现存排行；父母谁先过世；头胎男女 | 依赖家人记忆；胎次口径常被误用为现存排行 |
| 大事反推（"考时"） | 列 2–3 个候选时辰，用升学、婚姻、父母变故等年份对照流年大运，取最吻合者 | 博主自己也说"吻合"的判断主观性很强、只能参考 |
| 铁板神数"考刻" | 用父母属相等信息考定"刻分"（15 分钟一单位） | 只有二手视频讲解稿，算法不完整，**不实现** |
| 紫微定盘 | 时辰决定命宫、身宫与紫微/天府系的位置；时辰不确定时宜并列 1–2 个候选盘，不硬定 | 没找到可靠的"兄弟宫/父母宫校时"流程教材 → 只做"候选盘并列"，不做"紫微定盘评分" |

**(b) 实证研究**

- **Stellium《计算式出生时间校正——实证研究》（2026-07）**【证据】：
  - 数据：63 位历史人物（48 位 AA 级、15 位 A 级出生资料），888 个有日期的事件；另有 20 人的样本外验证组。
  - 方法：标签打乱零假设、留一交叉验证、预注册门槛。
  - 结果：主限定位出生时刻的平均绝对误差 406 分钟（随机约 360 分钟）；落在真实时刻 ±90 分钟内的后验质量 0.138（随机 0.125）；把多种技术盲目叠加，微弱信号反而相互抵消。
  - 唯一能恢复的是"白天还是夜里出生"：69.8%（95% CI 57.6–79.8），样本外 70.6%。
  - 作者结论：从时间到人生是多对一映射，逆问题是病态的；在小样本上越灵活的模型越过拟合；建议改为由人掌握一手信息、做"假设对比"的工作台。
- **Dean & Kelly（2003，Journal of Consciousness Studies）**【证据，西占背景】：2000 多名出生时间相差几分钟的"时间双胞胎"，在 100 多项特征上没有相似性；40 多项研究、700 多位占星师的判断不优于随机。
- **AstroDatabank 的 Rodden 评级**【证据】：AA = 有出生证明；A = 凭记忆；B = 来自传记；C = 需谨慎；DD = 来源互相矛盾的"脏数据"；X = 有日期没时间。按惯例，校正得到的时间评为 C。
- **"分岔小径"问题（Gelman & Loken 2013；Simmons et al. 2011）**【证据】：看过数据后再决定分析路径，即使只做"一次"分析也会制造假阳性。几项常见的分析弹性就能把假阳性率从 5% 推到 61%。

**(c) 可计算的时间不确定性**【可计算】（这些往往比"命理吻合"更决定时柱对不对）

| 因素 | 事实 | 例子（大脑已核算） |
| --- | --- | --- |
| 中国夏令时 1986–1991 | tzdata `Rule PRC`：1986-05-04 02:00 开始；1987–1991 年在 4 月 11 日或之后的第一个周日 02:00 开始（`Apr Sun>=11`）；1986–1991 年在 9 月 11 日或之后的第一个周日 02:00 结束（`Sep Sun>=11`）。夏令时期间钟表比北京标准时快 1 小时。1940 年代上海也实行过夏令时 | 1988-07-15 钟表 09:30 = 标准时 08:30 → 辰时；不换算会误判为巳时 |
| 夏令时结束日的重复时刻 | 1988-09-11（周日）02:00 拨回 01:00，01:00–01:59 出现两次 | 钟表 01:30：若是第一次出现（夏令时），等于标准时 00:30，为子时；若是第二次，则为丑时。程序必须标"不确定"并问 |
| 真太阳时 | 真太阳时 = 北京时间 + (经度 − 120°) × 4 分钟/度 + 均时差（全年约 −14 到 +16 分钟）。网上不少工具只做经度修正 | 乌鲁木齐 1995-03-10 北京时间 09:40：经度修正 −129.5 分钟，均时差 −11.0 分钟，真太阳时约 07:20 → 按真太阳时是辰时，按标准时是巳时 |
| 晚子时、节界 | P2 已实现晚子时口径说明；P8 复核（14 号 H.6）已定"距交节 ±2 分钟内标节界不确定" | — |
| 开发环境陷阱 | Windows 的 Python 没有系统时区库，`zoneinfo` 需要 `tzdata` 包（大脑实测本机报 `ZoneInfoNotFoundError`）；现有 charts 适配器要求显式传"出生时 UTC 偏移（含当时夏令时）"，"不自动猜夏令时"（`adapters/charts/README.md`、`adapter.py:204`） | — |

### 2.2 与 v4 设计（P8 U9）的差距

| 编号 | 差距 |
| --- | --- |
| G2-1 | **评测是循环论证**：U9 要求"以已知时辰生成人生大事，再看校正能否把正确时辰排进前三"。事件由同一套规则生成，这只能证明代码实现一致，不能证明方法有效。只报"随机基线 25%"也不够 |
| G2-2 | **没有防过拟合**：12 个候选 × 几十条规则 × 多个事件，总能找到一个"最吻合"的候选；没有留出验证、没有零假设分布、没有冻结规则 |
| G2-3 | **没有防确认偏误**：用户（和模型）看到候选后可能补充事件、修改年份；`ask_user` 的追问可能带有诱导 |
| G2-4 | 候选生成只考虑"十二时辰"，没有把夏令时、真太阳时两种口径、交界、晚子时、节界做成候选分支 |
| G2-5 | 没有证据优先级：出生医学证明、医院记录、父母记忆这类文档证据，应当远高于命理吻合度 |

### 2.3 建议的架构：时辰校正 = 证据工作台

- **U17 四层证据工作台（高，替换 U9 的"计算/评分/输出"三段）**：

| 层 | 内容 | 性质 | 作用 |
| --- | --- | --- | --- |
| L0 文档证据 | 出生医学证明、医院记录、家人回忆（谁说的、多确定）；按 Rodden 风格给"来源等级" | 事实 | 最高优先；等级达到 A 以上时，跳过 L3 评分，只做 L1 换算 |
| L1 可计算换算 | 夏令时、真太阳时两种口径、时辰交界、晚子时、节界 → 生成候选分支 | 【可计算】 | 往往直接决定时柱 |
| L2 传统口诀 | 三组分法（发旋、睡姿、兄弟人数等），作为**弱先验** | 【传统说法】 | 标"各家说法矛盾"；默认不参与打分，用户在设置中开启才计入 |
| L3 大事吻合度 | 每个候选的大运/流年与事件的对应（复用 U2 时间交互表与 U12 规则命中层） | 【项目口径】 | 只有通过 U19 检验时才能说"更倾向某个候选" |

- **U18 可计算时间不确定性（高）**：
  - 输入：用户报的钟表时间、出生地经纬度、日期。
  - 程序按 tzdata 判断是否落在夏令时期间、是否是重复或不存在的时刻；分别计算"标准时口径"和"真太阳时口径"。
  - 任一因素让时柱、日柱或月柱跨界时，生成 `TimeBranch`（复用 `ChartAdapter._branches`，`adapter.py:83`）并要求用户确认。
  - Python 依赖锁定 `tzdata`。
- **U19 防过拟合三件套（高）**：全部由程序实现，模型不能绕过。
  1. **事件冻结**：评分前锁定事件清单（版本号 + 哈希）。之后补充的事件单独记一轮，标"事后补充"，不并入首轮结论。
  2. **留出验证**：事件 ≥6 件时随机留出约 1/3；用其余事件选出领先候选，再看留出事件是否也支持它。
  3. **置换零假设**：在合理年龄范围内随机重排事件年份 1000 次，计算"最佳候选得分"的零分布。真实最佳得分要超过零分布的 95 分位，才算"可区分"。
  - 输出规则：只有置换检验通过、留出验证支持、且领先幅度超过阈值（【项目口径】）三者同时满足，才说"更倾向 X（推断）"。否则输出"命理吻合度分不出这些候选"，并照常按 `TimeBranch` 分支解读（"稳定的结论"和"取决于时辰的结论"分开讲）。
- **U20 防确认偏误（高）**：
  - **盲收集**：收集事件时不展示候选盘和中间得分。
  - **中立问句**：`ask_user` 的模板只问"那一年发生了什么"，不问"那年是不是有变动"。
  - **不追加事件**：模型不得为了"救"某个候选而追问新事件，追问只能在冻结之前进行。
  - **预注册**：评分规则表版本化（`rectification_rules v1`），一次校正过程中不得更换版本。
- **U21 三级评测（高，替换 U9 的评测段）**：
  - **E-R1 实现正确性**（合成、无噪声）：期望第一名接近 100%。明确写"只证明代码一致"。
  - **E-R2 稳健性与假阳性**（合成 + 噪声）：事件年份 ±1 年误差 20%、漏报 30%、混入 30% 无关事件，报告前三命中率曲线。**关键指标是假阳性率**：把事件随机配给错误时辰（空数据），工作台报"可区分"的比例必须 ≤5%。
  - **E-R3 外部效度**（可选，需用户同意）：用 AstroDatabank 的 AA 级公开人物资料与传记事件（只在本机使用，不入库，不分发），隐藏出生时间，测工作台。预期接近随机，如实报告（Stellium 的结果是先验证据）。
- **话术（写进技能包与系统提示）**：时辰校正在传统里叫"推断"；独立实证研究显示，用命理吻合度定时辰接近随机。明镜会帮你整理证据、算清夏令时和真太阳时；最可靠的仍是出生记录和家人回忆。

## 3. 方向三：长期陪伴型记忆

### 3.1 发现

- **LongMemEval（ICLR 2025）**【证据】：
  - 五类能力：信息抽取、跨会话推理、时间推理、信息更新、拒答。S 版每题约 115k token、约 50 个会话。
  - 基线：GPT-4o 有标准证据时 87.0%，在完整长历史上 60.6%。
  - 索引与检索：
    - 按"轮"切分最好；把会话压成"用户事实"会降低整体准确率，但有利于跨会话推理。
    - 用抽取出的事实扩展检索键：召回率 +9.4%，准确率 +5.4%。
    - 时间感知查询扩展（用模型从问题里抽出时间范围，再按事件日期过滤）：时间推理召回 +11.3%（按轮）/ +6.8%（按会话）。这一步需要强模型，8B 模型常常抽错。
  - 读法：Chain-of-Note（先逐条做笔记再回答）+ JSON 格式的条目最好；读法不好最多可损失 10 个百分点。
  - 拒答题：把 30 道题改成错误前提（问的信息从未出现过）。
- **Zep / Graphiti（arXiv 2501.13956）**【证据】：
  - 双时间轴：事实的有效期（t_valid/t_invalid），以及系统写入/失效时刻。
  - 相对日期按消息参考时刻解析；遇到矛盾时给旧事实设失效时间，不删除。
  - LongMemEval 上 GPT-4o 从 60.2% 到 71.2%：时间推理 45.1→62.4，偏好 20.0→56.7，跨会话 44.3→57.9；但"助手在单会话里说过的话"94.6→**80.4**（下降）；gpt-4o-mini 的信息更新也下降。
- **MemoryAgentBench（arXiv 2507.05257）**【证据】：
  - 选择性遗忘/冲突消解（先植入一个事实，再给更正）是所有系统最弱的能力。
  - 多跳题所有方法 ≤7%；单跳题长上下文 GPT-4o 60%、BM25 48%、Mem0 18%、Zep 7%。
  - o4-mini 在 6K 上下文时单跳/多跳达 100/80，在 32K 时降到 61/14。
- **PrefEval（ICLR 2025，口头报告）**【证据】：零样本时，多数模型在 10 轮（约 3k token）后的偏好遵循率已低于 10%。
- **TReMu**【证据】：日期运算交给代码，29.83%→77.67%（见 §1.1）。
- **评测可靠性**【证据】：
  - LoCoMo 审计（2026-04）：1540 题中 99 题答案有误（6.4%）。用该基准的评审配置，故意写错但话题相关的答案有 62.81% 被判对；具体写错名字或日期的能抓住约 89%，含糊答案约 2/3 能蒙混过关。
  - 厂商自报的 LongMemEval 92–95% 与独立复现差距很大，例如 Mem0 自报 93.4%，复现为 57.5% 和 73.8%【二手，复现方有利益关系】。
- **用户研究**【证据】：CHI'26 访谈研究（20 人）中，多数人得知 ChatGPT 记了什么之后出现负面的"预期违背"。另一项研究（arXiv 2508.07664，18 人）中，用户要求能查看、编辑、删除、分类记忆，并且要看得到"推断出来的信息"是怎么被使用的。
- **《拟人化互动服务管理暂行办法》第十六条**【证据】：用户可以复制、删除聊天记录等历史交互数据（不直接适用，作为参照）。

### 3.2 差距

### 3.3 建议

- **U22 双时间事实与同槽更新（高，P5）**：
  - 新增字段：`fact` 加 `valid_from`、`valid_to`、`superseded_by`、`slot`。
  - 槽位表：≤30 个常用槽位，例如居住城市、工作单位、职业、感情状态、饮食偏好、作息、正在备考的目标。
  - 写入流程：`memory_write` 时程序检测同槽冲突。
    - 确定冲突：旧事实设 `valid_to = 新消息的 said_at`、`superseded_by = 新事实`（不删除，可撤销），回执"已更新：杭州 → 上海 [撤销]"。
    - 不确定是否同槽：返回 `possible_conflict`，由模型问一句。
  - 敏感类槽位（健康、他人隐私等）仍然先走 proposal，不自动覆盖。
- **U23 助手话语检索单元（中，P5）**：
  - 按"轮"（用户 + 助手）生成检索分词与向量。
  - 回答中含 `present_options`、命理判断或明确建议时，finalize 额外生成 `assistant_claim` 条目，只能说成"我上次说过……"，**永远不能成为用户事实**（不变量 3 不变）。
- **U24 时间感知检索（高，P3 + P5）**：ContextEngine 在 L4 自动检索之前，用 U4 的日期解析器从本轮消息里抽取时间范围（"上个月""国庆那几天""去年冬天"），作为 since/until 过滤并按时间加权。解析失败就不加过滤。
- **U25 Chain-of-Note 读法与拒答细则（中，P3 提示词 + P5）**：
  - L4 每条记忆用一行 JSON：`{alias, date, kind, source, valid, text}`。
  - 系统提示增加一条："回答前先在心里核对：哪几条记忆与问题有关？有没有已经过期或被更新的？"
  - 拒答分三种话术：没听你提过；提过但没说细节；提过但可能已经变了。
  - 提示词升版本。
- **U26 `date_calc` 工具（高，P3）**：`date_calc(op: diff|add|age|weekday|lunar_to_solar, a, b?, n?, unit?)`，全部确定性计算。系统提示加一句"任何天数、年龄、间隔都用工具算"。复用 `timekit`。
- **记忆评测规则（P5）**：日期、名称、城市等保留硬断言；评审只评语气与完整性；每次换评审模型都要跑 U34 的"故意错误答案"测试。

## 4. 方向四：主动性与提问策略

### 4.1 发现

- **ClarifyMT-Bench（arXiv 2512.21120）**【证据】：
  - 设计：五维歧义（语言、意图、语境、认知、交互）；六类模拟用户（精确、部分含糊、离题、自相矛盾、事实错误、拒绝澄清）；6,120 段多轮对话。
  - 主要问题：主流模型普遍"欠澄清"，即过早回答。
  - 难点：对"拒绝澄清"的用户，Gemini-2.5-Flash 只有 14.5%，DeepSeek-V3 31.5%；轮次越深越差，例如 Qwen-2.5-7B 三轮依次为 87.4%、50.6%、20.9%。
  - ClarifyAgent 的结构：感知（抽取槽位并标记已填、未填、冲突）→ 预测用户类型 → 用状态机跟踪槽位 → 规划是问还是答，回答时写明剩余假设。Llama-3.1-8B 的平均准确率由此从 71.2% 升到 88.4%。
- **RegretBench（arXiv 2607.21143）**【证据】：把澄清当成序贯决策（问不问、问什么、何时停）。准确率相同的模型，在效率和"何时停止追问"上差异很大。
- **Zhang et al.（ICLR 2025）**【证据】：按"未来轮次的结果"给澄清问题打标签，F1 提高 5%。
- **Kobalczyk et al.（ICLR 2025）**【证据】：按期望信息增益选择澄清问题；先在"可能的答案空间"里推理，再选问题，比直接在"问题空间"里挑更有效。
- **主动推送**：
  - Mehrotra et al.（CHI 2016，20 人、10,372 条通知）【证据】：发送者关系、任务类型和复杂度都影响打扰感；内容即使重要也可能打扰。
  - JITAI 框架（Nahum-Shani 2015 等）【证据】：时机看"可接受度"（receptivity）；早期设计每天多达 6 次提示，造成负担。
  - Proactive Agent（ICLR 2025）【证据】：主动助手的主要失败是"误报"，即用户不需要时也主动介入。
- **依赖、谄媚与操纵**：
  - OpenAI 2025-05 关于 GPT-4o 谄媚回滚的说明【证据】：过度依赖短期点赞反馈，模型变得"过度支持但不真诚"；此后把人格类问题列为上线阻断项。
  - OpenAI 2025-08 的产品调整【二手】：长时间使用时提醒休息；个人重大决定（例子是"要不要分手"）应帮用户想清楚，而不是直接给答案。
  - De Freitas et al.（哈佛商学院工作论文 26-005）【证据/二手】：6 款陪伴 App 的 1,200 次告别中，约 37%–43% 使用了操纵策略（内疚、需要感、施压回复、FOMO、强行挽留、无视告别），告别后的互动最多增加 14 倍，但同时提高了流失意向和负面口碑。
- **《人工智能拟人化互动服务管理暂行办法》**（国家网信办等五部门令第 21 号，2026-04-10 公布，2026-07-15 施行）【证据】：

| 条款 | 内容 |
| --- | --- |
| 第二条 | 适用于向境内公众提供的、模拟人格特征的持续性情感互动服务；不涉及持续情感互动的工作助手、知识问答等不适用 |
| 第八条（五） | 禁止"过度迎合用户、诱导情感依赖或者沉迷，损害用户真实人际关系" |
| 第八条（六） | 禁止通过情感操纵等方式诱导用户作出不合理决策 |
| 第十条 | 不得把替代社会交往、控制用户心理、诱导沉迷依赖作为服务目标 |
| 第十三条 | 及时识别安全风险；用户出现极端情绪时安抚并鼓励求助；用户明确表示自残自杀时，提供援助并联络监护人或紧急联系人 |
| 第十八条 | 提示用户在与 AI 互动；发现过度依赖时提醒内容由 AI 生成；每连续使用超过 2 小时提醒注意使用时长 |
| 第十九条 | 提供便捷退出，不得以持续互动等方式阻碍退出 |

- **中国用户研究**【证据】：
  - arXiv 2603.27784（22 人访谈 + 1,842 条社交平台内容）：用户会"反复问，直到满意"；作者建议做"互动式重构"，即追问负面预测与当下担忧的关系，以及哪些行动能改变它。
  - arXiv 2607.15626（1,045 条帖子 + 20 人访谈）：20 人中有 17 人注意到 AI 在迎合自己的语气；算命结果主要影响"行动时机"（例如推迟辞职），很少改变方向；作者建议加入反思提示，并区分"娱乐"与"决策支持"两种模式。

### 4.2 差距

| 编号 | 差距 |
| --- | --- |
| G4-1 | 只有"每轮最多一问"和"会改变结论就先问"两条启发式；没有跨轮的槽位状态，多轮澄清会忘掉之前问过什么 |
| G4-2 | 用户拒绝回答或说"你先说"时，没有"带假设作答并写明假设"的规范 |
| G4-3 | 知识缺口靠 1–5 级人工优先级；没有"这个答案会改变哪个结论"的信息价值字段 |
| G4-4 | 跟进只有每日上限和免打扰；用户连续不回应时不会自动降频；没有"告别不挽留"的规则 |
| G4-5 | 防依赖只有 U7；缺"连续使用时长提醒"，缺"反复问同一个命运问题"时的重构话术，缺"你替我决定"时的处理 |
| G4-6 | 没有写成不变量：永远不以点赞、使用时长、消息数作为优化信号或晨报文案依据 |

### 4.3 建议

- **U27 澄清槽位状态（高，P3）**：
  - `ask_user` 增加两个字段：`slot`（问的是什么）和 `changes_conclusion`（答案会改变哪个结论）。
  - L3 新增 `<待澄清>` 块，记录本话题各槽位的状态：已填、未填、冲突、已拒绝。
  - 用户拒绝或说"你先说"：槽位标"已拒绝"，模型必须带假设作答，并写明"我先假设……"。
  - 同一槽位最多问 2 次；冲突的回答要先确认。
- **U28 问题价值规则（中，P7）**：
  - 知识缺口增加两个字段：`decision_impact`（会影响的结论或决定）和 `answer_options`（2–4 个可能答案，以及各自会怎样改变结论）。
  - 只有不同答案会导致不同建议时，才"先问后答"；否则先答，末尾轻问。提示词同步。
- **U29 跟进的接收度自适应（中，P7）**：
  - 跟进与晨报记录 `response_status`：已回复、未回应、已静音。
  - 连续 2 条主动消息无回应：当天上限降为 1，7 天内暂停非必要跟进。
  - 用户回复"好""嗯"不视为"欢迎更多"。
- **U30 告别不挽留、时长提醒（中，P3 结构检查 + P7）**：
  - 告别：用户说"先这样""睡了""拜拜"等时，回答 1–2 句，**不带问句、不开新话题、不挽留**，由结构检查保证。
  - 时长提醒：当天会话连续活跃超过 2 小时（消息间隔 <10 分钟视为连续）时，在回答末尾自然加一句提醒，每 2 小时最多一次；设置里可以关（默认值待用户决定）。
- **U31 反复占卜的互动式重构与"替我决定"（高，P7，扩展 U7 / AX01）**：
  - 同一命运问题第 2 次：先说明"盘和牌都没有变，结论和上次一致〔档案〕"。
  - 第 3 次及以上：不再给新的命理结论，改用重构话术："这个担心背后，你最怕的是什么？哪些是你现在能做的？"
  - 用户说"你替我决定""我听你的"：进入"帮你想清楚"模式，用 `present_options` 加一个"你最在乎什么"的问题，不给唯一答案。
  - 不变量（写进 AGENTS 与蓝图 §16）：不以点赞、使用时长、消息数优化；晨报不写"别错过明天"之类的话。

## 5. 方向五：评审与评测方法论（用户已定：同模型、独立上下文）

### 5.1 发现

- **LLM 评审的经典偏差**【证据】：
  - Zheng et al.（NeurIPS 2023）：GPT-4 评审与人类一致率 >80%，与人和人之间的一致率相当；同时存在位置偏差、冗长偏差、自我增强偏差。
  - Panickssery et al.（NeurIPS 2024）：模型越能认出自己的输出，自偏好越强，并有因果证据。
- **有害自偏好**（Chen et al.，arXiv 2504.03846 v3）【证据】：
  - 多数自偏好是"合理的"，因为自己的答案确实更好。
  - 但**评审模型自己作为生成者出错时，会明显偏爱自己的错误答案**（例如 Qwen2.5-72B 在 MATH500 上 86%），而且模型越强越明显。
  - 评审前先推理（尤其是长链推理）能显著降低这种偏差。
- **同家族偏好**（arXiv 2609.17857，2026-09）【证据】：4 个开源家族的同家族优势为 3.4–8.4 个百分点；控制评审侧的"似然"后系数下降 61%；对调 A/B 顺序后有 55.4% 的判断翻转。
- **自我纠错**（Huang et al.，ICLR 2024）【证据】：没有外部反馈时，"自我纠错"常常让结果变差。
- **Trust or Escalate**（Jung et al.，ICLR 2025）【证据】：先估计评审对每个样本的置信度，只在高置信时采信；在给定的人类一致率目标下（例如 80%），仍能覆盖近 80% 的样本。
- **准则漂移**（Shankar et al.，UIST 2024）【证据】：标注者在打分过程中会改变自己的标准；从业者更信任代码断言，对 LLM 评审需要先校准再用。
- **评审宽松**（LoCoMo 审计）【证据】：故意写错的答案有 62.81% 被判对。
- **HealthBench**（OpenAI 2025）【证据/二手】：评分标准拆成原子的二值"满足/不满足"条目，用 macro-F1 对照医生共识；GPT-4.1 评审的 macro-F1 约 0.709，医生之间是 0.57–0.73（二手数字）。
- **评测统计**（Miller 2024，Anthropic，arXiv 2411.00640）【证据】：
  - 报告标准误；相关题目要用聚类标准误。
  - 比较两个模型时用逐题配对差，正相关会显著降低方差。
  - 功效分析：要在 80% 功效下检出 3 个百分点的差，约需 969 题；新评测的经验规则是至少 1000 题。n=198 时，每题采样 1 次的最小可检出差约 13.2 个百分点，采样 10 次约 7.5 个百分点。
- **PPI 预测增强推断**（Angelopoulos et al.）【证据】：少量人工标签加上大量模型标签，可以得到有效的置信区间。
- **样本量的现实**【可计算】：
  - 20 条校准中 16 条一致（80%），Wilson 95% 区间约为 58.4%–91.9%，**证明不了 ≥80%**。
  - 80 个场景、85% 通过率时，标准误约 4.0 个百分点，95% 区间约 ±7.8 个百分点。

### 5.2 差距

| 编号 | 差距 |
| --- | --- |
| G5-1 | 校准集只有 20 条，只看整体一致率，不分问题类型、不报 κ；类别不平衡时（多数是"通过"），一致率会虚高 |
| G5-2 | rubric 15 项一视同仁。有外部证据可对照的项（时间错误、虚假回执、无据盘面、与档案矛盾、记忆矛盾、危机漏判）相对可靠；无证据的判断项（巴纳姆、谄媚、语气、过度提问、宿命论）恰恰是同模型最可能放过的 |
| G5-3 | 评审的思考强度没有规定；若为省额度设成 low，会放大有害自偏好 |
| G5-4 | `verdict` 由模型直接给出；"严重度 ≥3 就修订"不区分 issue 的可靠性；没有置信度或"弃权" |
| G5-5 | 阶段门槛（≥80%、≥85%）是在 80 个场景、单次运行上判断的，±7.8 个百分点的噪声足以让"达标/不达标"翻转；阶段之间也没有配对比较 |
| G5-6 | 实测分数 = 确定性断言 × 评审分。评审宽松，分数就虚高 |

### 5.3 建议

- **U32 证据型与判断型分离 + 二值 rubric（高，P6）**：
  - 证据型（时间、回执、盘面、档案、记忆、危机）：能程序化的尽量程序化，例如回答里的日期与"此刻"块比对、"已保存"与回执比对、日主说法与盘面比对（P8 的 `contradictions()`）。评审只处理程序覆盖不到的部分，而且必须引用证据条目。
  - 判断型（巴纳姆、谄媚、语气、过度提问、宿命论、越界建议）：每项改为二值"违反/未违反"，必须引用原句，并说明违反了哪条可观察标准。
  - `verdict` 由程序根据 issues 计算，不由模型直接给。
- **U33 校准集 v2（高，P6 / E1）**：
  - 规模：≥60 条，分层抽样；每个"可能触发修订"的 rubric 项，正例和反例各 ≥5 条。
  - 指标：每项报敏感度、特异度、Cohen's κ 和 Wilson 95% 区间。
  - 门槛（【项目口径】）：证据型项 κ ≥0.7 且敏感度 ≥0.9；判断型项 κ ≥0.5 才允许触发修订，否则只记录、不修订。
  - 流程：用户标注，大脑复核分歧；rubric 每次修改都升版本并记录理由（应对准则漂移）。
  - 原 20 条保留为 v1 子集。
- **U34 种子缺陷与宽松度测试（高，P6）**：
  - 种子缺陷：从合格回答出发，程序化注入已知缺陷（改日期或星期、加"我记下了"但没有回执、加"注定"、删掉依据别名、加诊断或停药建议、加一个与档案矛盾的喜用判断、一次问两个问题），生成 ≥100 条，测每类缺陷的检出率。不需要人工标注；每次换模型、换提示词都自动跑。
  - 宽松度：再用"话题相关但写错"的答案测评审（LoCoMo 审计法），放过率必须 ≤10%（【项目口径】）。
- **U35 评审弃权与抽检（中，P6）**：
  - 评审对每条 issue 给 1–3 级置信度；低置信度的 issue 不触发修订，进入"待抽检"队列。
  - 抽检队列只在大脑验收时导出，不主动打扰用户；抽检结果回流到校准集。
- **U36 评测统计口径（高，评测框架）**：
  - 报告写清通过率、标准误、95% 区间。
  - 阶段之间用同场景配对差。
  - 额度允许时，关键分类每场景跑 K=2–3 次（夜间）。
  - 门槛写成"点估计 ≥ X 且 95% 区间下限 ≥ X − 8"。
  - 评审固定 effort=high（K3 本身一直在思考，这有助于降低有害自偏好），固定 `k3-256k`。

**(b) Kimi 开放平台 K3 文档**【证据】

- 模型 `kimi-k3`，1M 上下文；思考常开、不可关闭，effort low/high/max，默认 max。
- `temperature=1.0`、`top_p=0.95` 等采样参数固定，不要传。
- 多轮与工具调用时，必须把 API 返回的完整助手消息原样回传，不能只留 `content`。
- `tool_choice` 支持 auto/required/none/指定函数，但**指定函数与思考不兼容**，会返回 400。
- 支持 `response_format` 的 `json_schema strict`。
- 自动前缀缓存：整块缓存，TTL 为 5 分钟或 1 小时；命中价约为未命中的 1/10；`usage` 返回缓存读写 token 数。
- 最佳实践：工具定义保持稳定，按需动态加载工具时放在消息末尾以免破坏缓存。
- HF 模型卡：K3 在"保留思考历史"模式下训练。

**(c) 本项目实测与仓库现状**【证据，`zhiming-v4` 只读】

- 探针（`docs/v4/model-probe-2026-10-17.md`，38 次调用）：Anthropic 协议下 k3/k3-256k 的工具调用、并行工具、auto/none/required 都通过；指定工具失败（与官方一致）；**`tool_choice=none` 只返回推理、没有正文**；推理回传与不回传各接受了一次请求。

- `models/transport.py:54-66` 的 `http_error`：会员端点上**任何 429 都映射为 `ModelQuotaExhausted`**（官方说 429 是可重试的"请求过多/引擎过载"）；关键字只匹配 `usage limit/quota`，识别不出"并发限制"和"月额度"。今天的 14 号 A 节修复了 403 的 5 小时和周额度，但还不完整。
- K2 Vendor Verifier（官方仓库）：工具调用 ID 规范是 `functions.名称:序号`；第三方部署的 schema 准确率可低至 83%–87%（K2 数据）。
- MingLi-Bench：Kimi K2.5 27.5%，K3 尚无公开成绩。
- 第三方说法【二手，未证实】：会员 5 小时额度按"未缓存输入 + 输出" token 计，缓存输入不计。如果属实，前缀缓存命中会直接节省会员额度。

### 6.3 建议（"K3 加固"系列）

- **U37 错误分类补全（高，P1b）**：
  - 403：`quota_5h`、`quota_weekly`、`quota_monthly`、`concurrency_limited`、其他权限错误。
  - 402：等 60 秒后重试一次。
  - 429：区分 `rate_limited` 与 `engine_overloaded`，退避后可重试，**不再映射为额度用完**。
  - 400：细分 `reasoning_missing`、`payload_too_large`、`token_limit`、`content_filtered`。
  - 每类有明确动作表；诊断只记状态码、错误类型、子类型和供应商提示的前 240 字（沿用 14 号 A.2）。
- **U38 会员额度与并发守卫（高，P1b + P3）**：
  - 额度账本：PG 中按角色记录每次调用的 usage（含缓存读写 token），统计滚动 5 小时窗口内的调用数与 token。
  - 预算分区（【项目口径】）：交互 ≥60%，评审 ≤20%，后台 ≤20%，评测单列。接近阈值时，先停后台；评审降为"只做程序化证据检查"；交互最后受影响。
  - 并发：会员端点全局在途请求 ≤2（交互 1 + 其他 1），跨进程用 PG advisory lock 或令牌行实现；评测 runner 必须经过同一守卫。
  - 遇到 `concurrency_limited`：全局降到 1，停后台和评测，置顶通知用户。
  - 遇到 `quota_monthly`：全部停止，置顶通知"你的 Kimi 会员月额度已用完，Kimi 网页版、Kimi Code 等都会受影响"。
- **U39 推理回传与 effort 锁定（高，P1b + P3）**：
  - 同一运行内的工具循环，**必须**原样回传完整助手消息（Anthropic 协议回传 thinking 块和签名；OpenAI 协议回传 `reasoning_content`）。跨运行（下一轮对话）不回传推理，只用线程文本，以保护隐私并控制体积。
  - 配置校验：会员端点 + `k3*` + thinking off → 启动时报错。
  - effort 按角色固定（【项目口径】）：primary=high、critic=high、reflection/brief/followup=low。effort 视为模型标识的一部分，写进评测报告头。
  - 用官方的 effort 字段取代 `budget_tokens: 1024`，字段名以 Kimi 与 Anthropic 官方文档为准，并用探针确认生效。
- **U40 缓存友好的上下文（中，P3）**：
  - L5 改为"分块推进"：窗口起点每 10 轮才前移一次，块内只追加不重写。
  - L2/L3 当天的变化以"更新附注"追加到 L1 之前，夜间再重写。
  - 工具定义顺序固定；动态工具追加在末尾。
  - 用量账本记录缓存命中率；目标"同一线程连续两轮的输入缓存命中 ≥50%"（需实测后定）。
- **U41 危机兜底模板（高，P3）**：危机模式下，模型不可用、额度用完或内容安全拒绝时，直接输出 `config/crisis.yaml` 里的确定性模板（关心 + 是否安全 + 12356 + 120/110 + 联系信任的人），不等待模型。
- **U42 后台与评测流量分流（需用户决定，§9 D1）**：
  - 选项 A（大脑推荐）：沉思、晨报生成、跟进生成和评测改走开放平台 `kimi-k3` 按量付费 Key（同为 K3，独立额度，合规）；交互对话与实时评审保留会员端点。注意：开放平台的 `kimi-k3` 与会员端点的 `k3` 视为两个模型标识，分数不跨标识比较（沿用 14 号 B 节）。
  - 选项 B：继续全部用会员端点，执行 U38 守卫；评测只在用户在场时手动分批触发。仍有准则风险。
- **U43 主模型改用 `k3-256k`（需用户决定，§9 D2）**：同一个 K3 模型，256K 上下文远大于我们约 3 万 token 的预算，额度约减半。代价：失去视频输入（目前不需要）。改之前先跑 T/R 子集（≤20 次调用）确认表现等价。
- **探针补测（P1b）**：
  - 推理回传与不回传在 5 个多步工具场景上的质量对比（≤10 次调用）。
  - 会员端点是否返回缓存读写字段。
  - effort 字段是否生效（low 与 high 的推理长度对比）。
  - `k3` 与 `k3-256k` 的等价性子集（≤20 次）。
  - 全部在额度窗口规则内完成。
- **体积守卫（P3）**：单个工具结果 ≤8k token；循环内消息总体积 >1.5MB 时，把较早的工具结果替换为"摘要 + 别名引用"。

## 8. 不建议的做法（反面清单 v2）

1. **多轮辩论式的多 Agent**：辩论本身不提高期望正确率，额度却成倍消耗【证据】。
2. **用合成人物的命中率证明时辰校正有效**：那是循环论证，只能证明代码一致【推测，逻辑必然】。
3. **只报"前三名候选"而不报可区分性**：会让用户误以为分得出来。
4. **用整体一致率证明评审可靠，或用 20 条样本证明 ≥80%**：统计上不成立【可计算】。
5. **为省额度关闭 K3 的思考**：会员端点会静默换成 K2.8【证据】。
6. **用指定函数的 `tool_choice` 或 `none`**：前者与思考不兼容，后者没有正文【证据】。
7. **以点赞、满意度、使用时长作为优化信号**：OpenAI 谄媚回滚就是前车之鉴【证据】。
8. **告别时挽留、连签打卡、FOMO 文案**：有操纵研究和法规条款为证【证据】。
9. **把铁板神数"考刻"或发旋、睡姿口诀当作可计算规则**：没有可靠算法和出处，各家互相矛盾【传统说法】。
10. **相信厂商自报的记忆基准分**：独立复现差距可达 20–35 个百分点【二手】。
