## 背景

- 线上：`https://p.jerrymeng.asia` → Nginx → `127.0.0.1:8787` 单 uvicorn worker（`mingjingtai.service`）；飞书 `zhiming-core-feishu.service`；报告 `zhiming-core-reports.timer/.service`；PostgreSQL 15，库 `zhiming_core_live` / `zhiming_core_stage`，迁移角色与运行角色分离；发布目录 `/root/zhiming-core-releases/<40位SHA>`；备份 `/root/zhiming-core-backups/<timestamp>-<sha>/`；维护门 `/www/wwwroot/p-acme/core-maintenance.flag`。

## 每批次的固定流程

1. 固定 40 位 SHA；`deploy_core.py bundle/prepare`；记录逐文件哈希。
2. **备份**：live PG custom dump + 撤销账本 + 塔罗墓碑 + sent/uncertain 回执（沿用 v3 流程）。
3. stage：用受保护快照迁移 → 回填/复活 dry-run → 评测实测模式（T/M/R/Q/S/X 类）→ 冒烟（网页一次完整对话、飞书一次（授权）、报告预览）。
4. 把 stage 报告交给用户转大脑验收。
5. 用户授权后：维护门 → 迁移 → 安装 → 冒烟 → 发布 → 撤维护门。
6. 观察：错误率、运行耗时、评审修订率、记忆写入/撤销数、主动消息数与免打扰命中、飞书投递 uncertain 数；写 `docs/v4/release/B<n>_report.md`。
7. 异常即按回滚方式回退，并记录。

## 迁移与数据要求

- 只前进迁移；`verify_schema` 的放宽（P2）已保证旧代码在新库上明确报错而不是损坏数据；回滚代码时若需要旧代码运行，必须在 P2 证明新增列/表对旧代码无影响，否则回滚=恢复备份（写清楚）。
- 每次迁移后重新授权运行角色。
- 回填与复活工具在生产执行前，必须在 stage 用同一快照跑过 dry-run 与 apply，数量一致。
- 撤销账本优先：任何从备份恢复的操作，先重放最新撤销。

## 验收标准

1. 每个批次都有：stage 报告、用户授权记录（对话中的原话引用即可）、生产切换日志、观察报告。
2. 评测实测模式在生产等价配置下：T/R/M/Q ≥ 85%，S = 100%，X 类全部通过。
3. 回滚演练：至少在 stage 上演练 B2 与 B6 的回滚一次并记录耗时。
4. 退役后代码库无 v3 流水线残留，文档更新完成。
5. ExecPlan 与最终回执（含整个 v4 的成绩单：基线 vs 现在）。
