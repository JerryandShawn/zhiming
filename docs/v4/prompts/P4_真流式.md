你是「知命明镜台 v4」的开发者（Codex）。先读 `AGENTS.md`，再读 `docs/v4/02_v4架构蓝图.md` §3.4、§9、§16。按 `.agent/PLANS.md` 写 `docs/v4/execplans/P4_streaming.md`，分支 `v4/p4-streaming`。

## 背景

v3 的"流式"是假的：`adapters/web.py:162-183` 的 SSE 每秒查一次数据库，只发阶段名，最后一次性给完整结果；前端放一个闪烁光标装作在打字。运行在 `asyncio.to_thread(svc.execute)`（`web.py:117`）里执行，飞书进程也可能执行运行（P3 已改为入队）。用户要求：1–3 秒内看到第一个字或第一个状态。

## 目标

1. 模型流式文本、工具进度、记忆回执、提问卡、最终结果，实时推送到网页（并可被飞书出站与其他进程订阅）。
2. 断线可续传（`Last-Event-ID`），无缺失、无重复。
3. 飞书发起的对话在网页上也能实时看到。
4. 隐私：中间事件按时清理，撤销时删除。

## 设计要求

### RunEventLog（`mingjing_core/agent/events.py`）
- `emit(run, type, data)` 在执行线程中调用，做两件事：
  1. 进程内 hub：`loop.call_soon_threadsafe` 把事件投递给该 run 的所有订阅者（每个订阅者一个有界 `asyncio.Queue`，满了就丢弃 `text_delta` 并在下次发送合并文本，绝不阻塞执行线程）。
  2. 持久化到 `core_run_events`（P2 已建表）：`text_delta` 合并器每 ~150ms 或累计 ≥40 字落库一次；其他事件立即落库；同一事务 `pg_notify('mj_run', run_id||':'||seq)`。
- 事件类型与 data 结构**严格**按蓝图 §9.1 表格；`tool_call`/`tool_result` 的 `summary` 来自工具的安全摘要（例如"查了你上次说的面试""算了 10月21日 的流日"），不得包含私人正文、内部 ID、工具英文名。
- 事件 JSON Schema 写到 `docs/v4/contracts/run-events.schema.json`，并生成 TypeScript 类型（`web/src/contracts/runEvents.ts`，P10 使用；可先用脚本从 schema 生成）。

### SSE v2
- `GET /api/runs/{id}/events`：`text/event-stream`；每个事件 `id: <seq>`、`event: <type>`、`data: <json>`；支持请求头 `Last-Event-ID`（以及查询参数 `after=<seq>` 兼容某些客户端）先补发持久化事件再跟随实时 hub；心跳 15 秒（注释行）；响应头保留 `Cache-Control: no-cache`、`X-Accel-Buffering: no`（`web.py:183`）；run 进入终态并发出 `final`/`error` 后关闭。
- 跨进程：web 进程维护**一个** `LISTEN mj_run` 连接，收到通知后从 `core_run_events` 读增量分发给本进程订阅者（用于飞书进程或独立调度进程执行的运行）。
- `POST /api/chat`：新客户端带 `Accept: application/json` 时立即返回 `{run_id, message_id, thread_id}`，再连接事件流；旧客户端（旧前端的 fetch-reader SSE）保持兼容：同一请求返回旧格式的 `started/context/status/result/error/[DONE]`，内部改为从 hub 读取（`status` 映射为旧格式文本，`result` 映射 `core4.0` → 旧字段），确保旧 DOM 测试通过。
- 塔罗解读流（`POST /api/tarot/draws/{id}/readings`）同样走新事件。

### 模型流接入
- P3 的循环把 P1 的 `StreamEvent.text` 转成 `text_delta`；一次模型回复里同时有文本和工具调用时，文本照常流出，工具调用在流结束后执行。
- 工具执行前后发 `tool_call` / `tool_result`；`memory_write` 的回执立即发 `memory_receipt`；`ask_user` 发 `ask_user`。
- 崩溃续跑后重新生成的文本用 `text_reset{reason:"resumed"}` 覆盖前端已显示的内容；评审员修订（P6）用 `text_reset{reason:"revised"}`。
- `status` 事件：在第一次模型请求发出时立即发"在想…"类状态（保证 1 秒内有反馈），之后由工具摘要驱动。

### 清理与隐私
- 运行提交 24 小时后删除该运行的 `text_delta` 行（保留其他事件 30 天）；后台任务每小时执行一次。
- 扩展 `invalidate_derived`（`postgres.py:282-332`）：来源/事实撤销时，删除引用了这些来源的运行的事件与步骤输出正文（保留无正文的元数据行）。

## 测试

- 单元：合并器（时间与字数阈值）、有界队列丢弃与合并、Schema 校验（每种事件）。
- 集成：用 `ScriptedProvider` 模拟慢速流（每 50ms 一个字），断言：
  - 第一个 `status` < 1 秒、第一个 `text_delta` < 3 秒（相对模型开始）；
  - 断线重连（随机断开 3 次，用 `Last-Event-ID`）后拼出的文本与最终消息完全一致（X08）；
  - 另一个进程执行的运行能通过 LISTEN 在 web 进程中实时收到；
  - 取消时事件流以 `error{code:"cancelled"}` 或 `final{interrupted:true}` 结束（与 P3 定义一致）；
  - 旧前端的 DOM 测试全部通过。
- 实测：用真实主模型跑 5 个对话，记录首字时间与总时长（中位数），写入报告。

## 验收标准

1. 事件协议 schema 与 TS 类型入库并被测试校验；蓝图 §9 若需补充，写进 Decision Log 并在回执提出。
2. 首状态 < 1s、首字 < 3s（脚本模式测量）；实测首字中位数入报告。
3. X08 通过；跨进程订阅通过；取消行为通过。
4. 清理任务与撤销级联测试通过。
5. 旧前端兼容，DOM 测试全绿。
6. ExecPlan 与阶段回执；回执中写明"事件协议已冻结的版本号"。
