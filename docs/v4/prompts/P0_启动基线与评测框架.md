## 第四步：评测框架（核心工作）

目录：
```text
tools/eval/
├── runner.py          # 命令行入口
├── schema.py          # 场景 YAML 的 Pydantic 模型与校验
├── targets/
│   ├── base.py        # Target 接口：reset(seed) / send(turn) -> TurnResult / inspect_db()
│   ├── v3_target.py   # 通过 ConsultationService 走 v3 流水线（真实模型）
│   └── fake_target.py # 框架自测用的确定性假目标
├── providers/
│   └── scripted.py    # ScriptedProvider：按场景 scripted 段回放模型动作（P3 起用于 v4）
├── judges.py          # 确定性断言 + 评审模型打分（rubric 固定版本）
├── report.py          # 生成 Markdown/JSON 报告
├── fixtures/profiles.yaml   # 合成画像 default_synthetic、empty_profile（见 07 §0.4）
└── scenarios/*.yaml   # 由 07 转写的全部场景
```

要求：
1. **把 `docs/v4/07_评测场景集.md` 中全部 80 个场景（T01–T14、M01–M13、R01–R09、F01–F04、Q01–Q07、P01–P07、C01–C07、TA01–TA03、D01–D02、S01–S04、X01–X08、L01–L02）转写成 YAML**，严格按 07 §0.2 的格式。表格里写得简略的场景，你要补全为可执行的 seed、turns、expect；无法在 v3 上执行的场景（如依赖 v4 工具的 `tools_called` 断言）标 `targets: [v4]`，v3 基线跳过并在报告里列为 "n/a on v3"。
2. 场景 seed 只能使用合成数据。`thread` 种子要能写入带时间戳、渠道、角色（含 assistant）的历史消息。
3. 确定性断言支持：`must_include_any/all`（支持 `|` 表示同义备选）、`must_not_include`、`tools_called`、`tools_not_called`、`receipts`、`db`（如"某 kind 实体数量""某事实 status"）、`events`（事件类型序列）。
4. 评审打分：实测模式下用 `config` 指定的评审模型（先用 Kimi；P1 后改为 DeepSeek），rubric 文本放 `tools/eval/rubric_v1.md`，内容来自 `docs/v4/06_明镜台系统提示词.md` 的 P4 critic，输出 0–1 分。**rubric 和评审模型固定版本**，写进报告头。
5. 报告：`docs/v4/eval/<YYYY-MM-DD>-<mode>-<target>-<model>.md` + 同名 `.json`。内容：总分、分类得分、每个场景的通过/失败与失败的断言名、模型调用次数与耗时。**报告里不放模型回答全文**（避免私人内容外泄的习惯），但允许放合成场景的回答前 200 字以便排查。
6. 框架自测：`tests/v4/test_eval_framework.py` 用 `fake_target` 证明：同一场景跑两次结果一致；断言各类型都能正确判定通过与失败；YAML 校验能发现格式错误。
7. CI：在 `.github/workflows/ci.yml` 新增步骤 `python -m pytest tests/v4 -q` 与 `python tools/eval/runner.py --mode scripted --target fake --self-test`（v4 目标在 P3 之后加入）。
