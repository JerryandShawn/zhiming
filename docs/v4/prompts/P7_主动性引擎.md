# P7 · 主动性引擎：知识缺口、初次相识、跟进、个性化晨报

> 前置：P5 已合并（依赖画像、知识缺口、沉思）。飞书卡片交互在 P9，本阶段先用纯文本投递。

---

你是「知命明镜台 v4」的开发者（Codex）。先读 `AGENTS.md`，再读 `docs/v4/02_v4架构蓝图.md` §7、§13（主动消息部分）、§16，`docs/v4/06_明镜台系统提示词.md` 的 P1"主动提问与引导"、P2 onboarding、P5 brief、P6 followup。按 `.agent/PLANS.md` 写 `docs/v4/execplans/P7_proactive.md`，分支 `v4/p7-proactive`。

## 背景

用户希望助手"有主观能动性"：不懂就主动问、逐渐引导、记得约定的事并主动来问。v3 唯一的主动行为是四种定时报告（`adapters/channels/reports.py:62-75`），`FinalAnswer.follow_up` 只是印在答案里的一句话，没有任何程序会在那个时间点真的来找用户。

**用户已确认：** 晨报 + 约定的跟进；每天主动消息最多 2 条（不含晨报）；22:00–08:00 不打扰；一句话可关闭某类提醒；允许通过飞书主动联系。首次见面时由助手询问彼此的称呼。

## 目标

1. 知识缺口体系（§7.1）进入上下文 L3，驱动"每轮最多一个自然的问题"。
2. 初次相识流程（§7.2，提示词 06 P2），可暂停/继续。
3. 跟进与提醒的生成、调度、发送、跳过、关闭（§7.3）。
4. 晨报与周/月/季报改为 v4 运行种类 `brief`，个性化且历法准确（§7.4）。

## 设计要求

### A. 知识缺口（`mingjing_core/agent/proactive.py`）
- 实体 `knowledge_gap`（字段见 §7.1）；初次相识时创建初始缺口（称呼、出生时辰精度、出生地、职业/学业、感情状况、最在意的事、沟通偏好、作息）。
- ContextEngine L3 显示 open 缺口 Top5（按优先级与冷却）；模型提问后（回答末尾的问题或 `ask_user`）由 finalize 判断是否命中某缺口（模型在回答中引用 `〔g#〕` 别名，或 `ask_user` 参数带 `gap_id`），标记 `asked`、记录 `asked_at`，冷却 3 天。
- "先别问了"（规则 + 模型识别）→ owner 设置 `questions_paused_until = now + 7d`，L3 不再显示缺口；系统提示词中"每轮最多一个问题"的约束同时由结构检查保证（P6）。
- 用户回答后，沉思任务把缺口标为 `answered` 并写事实。

### B. 初次相识
- 触发：画像为空且该 owner 从未完成过 onboarding（owner 设置 `onboarding: {status: not_started|in_progress|done|paused, step}`）。
- 实现方式：在 system 提示词后叠加 `prompts/onboarding.md`；当前步骤与已知信息写进 L3；每轮结束根据已写入的事实推进 `step`；用户说"先到这/改天"→ `paused`，下次打开时温和地问是否继续（一次）。
- 出生资料步骤：调用 `profile_update_request` 生成确认卡（网页 P10、飞书 P9 渲染；本阶段在旧前端中可通过现有资料确认入口完成）。
- 第 6 步（主动联系偏好）用 `ask_user` 选项：`可以` / `晨报换个时间` / `先别主动找我`，结果写 owner 设置 `proactive: {brief_time, followups_enabled, quiet_hours:[22:00,08:00], daily_cap:2}`。
- 结尾"见面礼"：有确认出生资料时调用 `chart_compute` 给日主与一句性格底色（注明口径）。
- 脚本场景 Q01 + 新增 3 个 onboarding 场景（中途暂停、跳过出生资料、只想直接问问题）。

### C. 跟进与提醒（`mingjing_core/application/followups.py`）
- 调度：后台任务每分钟扫描 `followup/reminder` 的 `due_ms`（P5 新增的迁移 0008 已建 due 表达式索引）；对 15 分钟内到期的项创建 `kind=followup` 运行（`lane=background`，`operation_id=followup:<id>:<due>`，保证只生成一次）。复用报告 worker 的租约写法（`adapters/core_report_worker.py:33, 51`）。
- 生成：提示词 `prompts/followup.md`（06 P6）；模型可以输出 `SKIP`（例如用户已经聊过结果）→ 跟进 `skipped`，不发送。
- 发送：生成的文本作为线程中的助手消息（`kind=followup`），并通过 Outbox 投递到飞书（`OutboxService.prepare_delivery`，`adapters/delivery.py:58`）；**领取时**（`claim_delivery`，`delivery.py:92`）重新核对：来源未撤销、跟进仍 active、不在免打扰时段（落在 22:00–08:00 → 顺延到 08:30）、当天主动消息未达上限（超限 → 次日 08:30）；健康/金钱类跟进的飞书预览首句不得含具体内容。注意 v3 Outbox 的 `_fresh`（`delivery.py:45-56`）要求依赖完全不变，跟进消息需要改为"只核对撤销与有效性"，否则用户一聊天跟进就过期——写清楚改法与测试。
- 关闭："别再提醒这个/这类" → 模型调用 `followup_skip` 或设置 owner `followups_muted_topics[]`；也提供 API `POST /api/followups/{id}/cancel`。
- 提醒（`set_reminder`）：用户明确要求的提醒按时发送，不受每日上限约束，但仍受免打扰（除非用户明确要求在该时间，例如"明早 6 点叫我"——此时尊重用户指定时间）。
- 场景 P01–P07 全部通过。

### D. 晨报与周期报告
- 新运行种类 `brief`：复用 `ReportScheduleService`（`application/report_schedules.py:49, 148`）与 `domain/report_schedules.py` 的 `schedule_on_day / report_period / next_schedule`（`:75, 96, 106`）；准备时间仍为发送前 15 分钟。
- 提示词 `prompts/brief.md`（06 P5）；输入：此刻块（**发送时刻**的，不是准备时刻的）、画像、L3、今日流日（调用 `chart_compute`）、本周期情景摘要（周/月/季报）。
- 报告正文作为线程助手消息（`kind=brief|report`），通过 Outbox 投递；归档到现有报告页（`/api/reports` 兼容）。
- 2026-10-10 晨报（调休上班日）与 2026-10-17 晨报（周六、明天重阳）作为验收样例（T13、P07）。
- v3 的报告路径保留到 P11，按 owner `runtime` 路由。

## 验收标准

1. 脚本模式：Q01–Q07、P01–P07、T13 + 新增 onboarding 场景全部通过。
2. 实测（冻结时钟 + 合成画像）：生成 5 条跟进与 3 份晨报样例，附在证据目录（合成数据），由用户和大脑审阅语气。
3. 免打扰与每日上限的属性测试（随机生成 1000 个时间点/计数组合，用 `FrozenClock`）全部通过。
4. 不发送任何真实飞书消息（测试用传输替身）；stage 发送验证需用户授权并指定接收人。
5. ExecPlan 与阶段回执。

## 何时停下来问用户

- stage 上做真实飞书主动消息验证前（需要授权与时间窗口）；
- 晨报默认时间是否保持 07:00。
