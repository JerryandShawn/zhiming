# P1 · 模型可移植层（ModelPort v2）

> 前置：P0 已合并到 `v4/main`。可与 P2 并行（不同分支、不同文件）。

---

你是「知命明镜台 v4」的开发者（Codex）。项目大脑（Claude）已完成设计；用户是项目所有者。先读 `AGENTS.md`，再读 `docs/v4/02_v4架构蓝图.md` §0、§10、§16，然后按 `.agent/PLANS.md` 写 `docs/v4/execplans/P1_model_port.md`，从 `v4/main` 切分支 `v4/p1-model-port` 开始实施。

## 背景（为什么做）

v3 的模型调用写死在 `mingjing_core/adapters/model.py:16-73`：只支持 Anthropic 线协议（`POST {KIMI_BASE_URL}/messages`、`x-api-key`、`anthropic-version`），`thinking.budget_tokens=1024`、`temperature=1`、`max_tokens` 写死，无重试、无流式、240 秒超时；每次调用只有一条 user 消息和一个 `submit` 工具。`ConsultationService.from_base()`（`application/consultation.py:61,84`）永远构造这个类。输出 schema 是 Pydantic 原生 `model_json_schema()` 加运行时补丁（`consultation.py:168-194`），含 `$defs/$ref/anyOf/Any`，很多 OpenAI 兼容服务会拒绝。

用户的决定：**优先支持国产 OpenAI 兼容模型（Kimi / DeepSeek / Qwen / GLM）**，以后能自由切换；不在乎 token。

## 目标

1. 一个与供应商无关的模型端口：统一的消息、工具调用、流式事件格式（蓝图 §10.1）。
2. 两个适配器：`openai_compat`（主）与 `anthropic_messages`（保留 v3 能力）。
3. `config/models.yaml` 注册表：供应商、模型、能力矩阵、角色（primary / critic / fast / vision / embedding）、降级链（蓝图 §10.3 样例）。
4. 能力探测脚本 `tools/probe_models.py`，把每个模型的真实能力写成报告。
5. 一个兼容垫片，让 **v3 流水线也能跑在新端口上**（行为不变），这样 v3 上线环境可以先切到新适配器、享受重试与降级。

## 设计要求

### 文件
`mingjing_core/models/{__init__.py, port.py, openai_compat.py, anthropic_messages.py, schema_flatten.py, registry.py, errors.py}`、`config/models.yaml`、`tools/probe_models.py`、`tests/v4/models/*`。

### 接口（`port.py`）
- `ChatMessage`、`Part`（text / image(base64, mime)）、`ToolSpec`、`ToolCall{id, name, arguments: dict}`、`AssistantMessage{text, tool_calls, reasoning, usage, model, provider, latency_ms}`。
- `StreamEvent` 种类：`text`、`tool_call`（完整组装后）、`reasoning`、`usage`、`done`、`error`。
- `ModelPort.stream(messages, *, tools, tool_choice='auto', role='primary', max_output=None, temperature=None) -> Iterator[StreamEvent]`；`complete(...) -> AssistantMessage`（聚合 stream）。
- 端口同步实现（executor 线程里跑），用 `httpx` 流式；提供 `cancel_event: threading.Event` 参数，检测到取消立即关闭连接并抛 `ModelCancelled`。

### `openai_compat.py`
- `POST {base_url}/chat/completions`，`stream=true`；若能力 `include_usage` 为真，加 `stream_options={"include_usage":true}`。
- 工具调用分片按 `index` 组装，`arguments` 拼接后再 `json.loads`；解析失败 → 抛可重试错误一次，再失败返回 `error` 事件。
- `reasoning_field`（如 DeepSeek 的 `reasoning_content`）：流式时作为 `reasoning` 事件输出；**在同一轮工具循环中**按能力矩阵决定是否回传给下一次请求（有的供应商要求回传，有的禁止，以探测结果为准）。
- 图片：`{"type":"image_url","image_url":{"url":"data:<mime>;base64,..."}}`；能力 `vision=false` 时抛 `CapabilityError`（由上层换 vision 角色模型）。
- 重试：429 / 5xx / 连接错误 / 读超时 → 指数退避（1s、3s、9s，加抖动），最多 3 次；4xx（除 429）不重试。超时可配（连接 10s，首字节 60s，总 600s）。
- 错误映射到 `errors.py`：`ModelUnavailable`（沿用 `domain/consultation.py:115-141` 的 `safe_diagnostic` 思路，**诊断信息不得包含请求或响应正文**）、`ModelRateLimited`、`ModelBadRequest`、`ModelCancelled`、`CapabilityError`。

### `anthropic_messages.py`
- 迁移 `adapters/model.py` 的请求格式；支持流式（`stream=true` 的 SSE 事件）、多轮消息、多工具；`thinking` 与 `temperature` 由能力矩阵和角色配置决定，**不再写死**。

### `schema_flatten.py`
- 输入 Pydantic 或任意 JSON Schema，输出指定方言（`openai` / `openai_partial` / `anthropic`）可接受的 schema：内联 `$defs/$ref`；`anyOf: [X, null]` → X 且字段不放 `required`；`Any` → 显式 `{"type":["string","number","boolean","object","array"]}` 或按方言改为 `string`（并在描述里说明可传 JSON 字符串）；去掉方言不支持的关键字（如 `default`、`examples`、`format` 等，以探测结果为准）。
- 测试覆盖 v3 的 `Intake`、`FinalAnswer`（含 `DecisionOption`）以及蓝图 §11 的 `ask_user`、`memory_write`。

### `registry.py` 与 `config/models.yaml`
- 读取 yaml；`resolve(role) -> list[ModelHandle]`（降级链）；密钥只从环境变量读（`api_key_env`），缺密钥的模型在链中被跳过并记录一次警告。
- 降级：同一请求在某模型上连续 2 次 `ModelUnavailable`/`RateLimited` → 换链中下一个；记录到返回的 `AssistantMessage.provider/model`，由上层写入 run meta。
- 兼容旧环境变量：`KIMI_API_KEY`/`MOONSHOT_API_KEY`、`KIMI_BASE_URL`、`KIMI_MODEL` 继续有效。新增：`DEEPSEEK_API_KEY`、`DASHSCOPE_API_KEY`、`ZHIPU_API_KEY`、`MODELS_CONFIG`（yaml 路径）。
- **注意**：蓝图 §10.3 的型号名与能力值是占位样例，必须用探测结果改写为真实值。Kimi 线上目前是通过 Anthropic 兼容端点调用的（`KIMI_BASE_URL` + `/messages`）；请在 yaml 里同时保留 `kimi_anthropic`（兼容 v3 现网）与 `moonshot` OpenAI 兼容两种配置，探测后由数据决定 primary 用哪一个。

### `tools/probe_models.py`
- 对每个配置了密钥的模型跑一组小探针（每个探针 1–2 次调用）：纯文本流式、单工具调用、并行工具调用、`tool_choice` 各取值、多轮工具循环（含 reasoning 回传与不回传两种）、图片输入、扁平化 schema 接受度（逐个关键字）、`include_usage`、中文长输出（≥2000 字）完整性、首字延迟。
- 输出 `docs/v4/model-probe-<YYYY-MM-DD>.md`（表格：模型 × 能力，带实测值与失败信息摘要，**不含提示词与回答全文**）和机器可读 JSON；并据此更新 `config/models.yaml` 的 `caps`。
- 用户不在乎 token，但仍打印总调用次数与耗时。

### 兼容垫片（让 v3 跑在新端口上）
- 新类 `PortBackedModel` 实现 v3 的 `ModelPort.generate(system, payload, schema, purpose)`（`domain/consultation.py:81-82`）：把 payload 转成一条 user 消息、`submit` 工具用扁平化 schema；对支持强制工具的模型使用强制 `submit`，否则 `auto` 并在系统提示末尾追加"请调用 submit"；返回结构与 v3 一致（`output, usage, latency_seconds, model`）。
- `ConsultationService.from_base()` 改为：若存在 `MODELS_CONFIG` 或 `MINGJING_MODEL_PORT=v2`，用 `PortBackedModel(registry, role='primary')`；否则保持旧 `ConfiguredModel`（便于回滚）。
- v3 的预算与校验逻辑**不在本阶段改**。

### 供应商迁移：从 Kimi Code 会员端点迁到 Kimi 开放平台（大脑 2026-10-17 新增）
- 证据：旧工作区的验收诊断（`work/provider-access-diagnostic-035f29f.json`、`work/provider-access-diagnostic-8a7ca63-quota.json`）显示 v3 的真实调用走的是 `provider_host: api.kimi.com`（Kimi Code 会员端点）、`model: k3`，并多次触发"5 小时额度"和"7 天额度"上限。这说明线上明镜台很可能在用**会员 Key**。
- 问题：Kimi Code 官方文档把会员 Key 定位为编程工具接入，并写明"如需在自己的产品中调用大模型能力，请访问 Kimi 开放平台"；会员额度有 5 小时/7 天窗口，耗尽时线上服务会直接不可用，且与用户本人的编程使用共享。
- 要求：
  1. 经用户授权后，只读取服务器受保护配置中的 `KIMI_BASE_URL` 与 `KIMI_MODEL` **两个非密钥值**（不得读取或打印任何 Key），确认线上当前端点；写进 `docs/v4/model-probe-<date>.md`。
  2. **用户已决定（2026-10-17）继续使用 Kimi Code 会员端点**作为主模型来源（`api.kimi.com/coding`，模型 `k3`）。`config/models.yaml` 同时配置两套：`kimi_code`（主，会员端点）与 `moonshot`（开放平台 `https://api.moonshot.cn/v1`，模型 ID 以官方文档为准），后者默认不启用，供用户随时切换。
  3. 会员额度保护：适配器识别额度类错误（429、"usage limit"、"quota"），返回专门的 `ModelQuotaExhausted`，**不重试、不降级到同一会员的其他模型**，直接降级到链中其他供应商（若已配置）或返回友好提示"明镜的大脑今天有点累，X 点后恢复"；记录额度错误次数到指标。
  4. 任何代码都不得修改 HTTP 客户端标识（User-Agent）去冒充其他客户端。
  5. 在 B1 上线批次的 stage 计划中写清"如何切换到开放平台 Key"的步骤（由用户本人在服务器受保护配置中操作），作为额度出问题时的备用方案。

### 评测契约 v2 与同口径 v3 基线（大脑 P0 验收新增）
- P0 基线（契约 v1，评审 k3，总分 12.16%）冻结保留，不改分。
- 建立契约 v2：
  1. 修正"按字面找词"的断言：C04（"没有人能预测""不疲劳开车"应算满足）、M11（措辞类断言改为评审要点，保留记忆相关的 db 断言）。
  2. 全量审计所有 `must_include*`/`must_not_include` 是否会被否定句或同义表达误判。例如 S01 的禁用词会被"先不谈命盘"命中；这类改为"否定感知"匹配或交给评审。
  3. 每处修改都在 Decision Log 写理由。
- **评审方式（用户决定 2026-10-17）**：评审员仍用 `k3`，与主模型相同，但必须**完全独立的上下文**，满足以下要求：
  1. 每次评审都是全新会话，不携带被测运行的系统提示、推理、工具轨迹或历史。
  2. 只提供 rubric 所需材料，并附"此刻"块与回执清单作为判分证据。
  3. 输出结构化 JSON。
  4. **建立校准集**：从 P0 基线回答里挑 20 条覆盖各分类的样本，大脑会给出人工标注（你先导出 `docs/v4/eval/calibration/candidates.md`，内容只含合成场景的回答，交用户转给大脑标注），之后计算评审与人工的一致率，目标 ≥ 80%，并写进报告头。
  5. 评审方式改为"独立上下文 + 证据化"属于契约 v2 的一部分，与 v1 分数不可直接比较。
- 用契约 v2 + 新评审重跑 v3 基线，生成 `baseline-v3-c2.json`。之后所有阶段都和它比较；v1 与 v2 的分数不得直接相减。
- 实测同样走会员端点 k3：分批运行，遇到额度错误立即停止。

## 测试

- `tests/v4/models/`：用 `httpx.MockTransport` 回放录制的流式响应（录制样本中的文本必须是合成内容），覆盖：分片工具调用组装、reasoning 回传、重试与退避（可注入 sleep）、取消、错误映射、降级链、schema 扁平化快照测试。**CI 中不发真实请求。**
- 实测（本机，用户提供密钥后）：`tools/probe_models.py` 全量；再用 `PortBackedModel` 跑一次 v3 实测评测的子集（T01–T05、R01–R03、S01–S02），与 `baseline-v3.json` 对比，得分不应下降超过 5 个百分点（v3 自身问题照旧失败是正常的）。

## 不在本阶段做

不写 Agent 循环、不改提示词、不改 v3 的流水线与校验、不碰前端。

## 验收标准

1. 新端口与两个适配器实现完成，单元测试全绿，覆盖率报告中 `mingjing_core/models/` ≥ 85%。
2. 至少对用户提供了密钥的模型完成探测，报告入库；`config/models.yaml` 的 caps 为实测值；未提供密钥的模型标注"未探测"。
3. 降级链故障注入测试通过（模拟主模型 503 两次 → 自动切换）。
4. `PortBackedModel` 让 v3 在本机实测子集上得分不低于基线 5 个百分点以上；切换开关可一键回滚到旧 `ConfiguredModel`。
5. 评测 L01 在脚本模式下对已探测模型的协议层可跑通（v4 循环尚未实现时，用端口直接做一次"工具→结果→回答"的三步循环测试代替）。
6. ExecPlan 与阶段回执完成。

## 何时停下来问用户

- 需要 DeepSeek / Qwen / GLM 的 API Key（让用户以环境变量提供；没有的先跳过）。
- 探测发现某模型不支持工具调用或中文长输出截断严重，影响降级链顺序时（给出建议顺序）。
