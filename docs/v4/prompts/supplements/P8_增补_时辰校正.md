## 背景（证据）

1. **实证**：Stellium 的计算校正研究（2026-07，预注册）：63 位有出生证明级数据的人物、888 个有日期的事件，留一交叉验证并设标签打乱的零假设。所有定时技术定位出生时刻都在随机水平：主限平均误差 406 分钟，随机约 360 分钟。只有"白天或夜里出生"能分到约 70%。作者结论：逆问题是多对一、病态的，模型越灵活越过拟合。
2. **背景**：Dean & Kelly（2003）研究了 2000 多名出生时间相差几分钟的"时间双胞胎"，在 100 多项特征上没有相似性。
3. **统计**：看过数据后再选分析路径，会制造假阳性（Gelman & Loken 的"分岔小径"问题）。
4. **传统方法**【传统说法】：三组时辰分法（发旋、睡姿、兄弟人数等）、六亲口诀、"考时"（列 2–3 个候选、用大事对照）。各家说法互相矛盾，**没有找到可靠的古籍原文出处**。
5. **可计算的不确定性**【可计算，大脑已核算】：
   - tzdata 的中国规则 `Rule PRC`：1986-05-04 02:00 起实行夏令时；1987–1991 年在 4 月 11 日或之后的第一个周日开始，1986–1991 年在 9 月 11 日或之后的第一个周日 02:00 结束。
   - 1988-07-15 钟表 09:30 = 北京标准时 08:30（辰时）；不换算会误判为巳时。
   - 1988-09-11 01:00–01:59 出现两次：第一次为夏令时，等于标准时 00:00–00:59（子时）；第二次为标准时（丑时）。
   - 乌鲁木齐 1995-03-10 北京时间 09:40：经度修正 −129.5 分钟，均时差约 −11.0 分钟，真太阳时约 07:20（辰时），而按标准时是巳时。
6. **现有代码**：
   - charts 适配器要求显式传"出生时 UTC 偏移（含当时夏令时）"，"不自动猜夏令时"（`adapters/charts/README.md`、`adapter.py:204`）；
   - 时间分支 `ChartAdapter._branches`（`adapter.py:83`）；
   - 稳定性 `_stability`（`adapter.py:459`）；
   - `TimeBranch.input_precision` 取值为 `exact|approximate|interval|unknown`（`domain/calculation.py:73`）。
   - Windows 开发机的 Python 没有系统时区数据，`zoneinfo` 需要 `tzdata` 包。

## 设计要求

### A. 数据模型

- 新实体种类 `rectification`（加入 `ENTITY_KINDS`），字段：

      {id, subject, status: collecting|frozen|scored|confirmed|abandoned, round: 1|2,
       birth_input: {date, reported_time, precision, place: {name, lon, lat, tz}, clock_basis: clock|standard|unknown},
       documents: [{kind: certificate|hospital|family_memory|self_memory, reported_time, who, certainty: sure|roughly|unsure, grade}],
       events: [{id, type, year, month?, certainty, source_fact_id?, added_in_round}],
       frozen: {at, events_hash, rules_version} | null,
       result: {...§H} | null,
       confirmation: {chosen_candidate, at, profile_request_id} | null}

- 事件类型（沿用 U9）：升学/毕业、入职/离职、结婚/分手、生子、搬迁、亲人重大变故、重大疾病或手术、重大财务事件。
- 出生地经纬度：取用户确认的出生地；无法解析时请用户确认城市。**不默认任何城市。**
- 撤销与遗忘：事件来自事实时，记 `source_fact_id`；事实被撤销后，对应事件标记失效，已完成的结果标"依据已变化，需要重算"。扩展 `invalidate_derived` 覆盖这个新实体。

### B. L0 文档证据（最高优先）

- 来源等级（Rodden 风格，项目口径）：

  | 来源 | 等级 |
  | --- | --- |
  | 出生医学证明、医院记录 | AA |
  | 父母清楚记得、误差 ≤15 分钟 | A |
  | 家人大概记得 | B |
  | 本人听说、模糊 | C |
  | 多个来源互相矛盾 | DD |

- 达到 A 级及以上：**跳过 L3 评分**，只做 §C 的换算核对，结果为"以记录为准"。
- DD 级：把矛盾的几个时间都列为候选，进入 §C。

### C. L1 可计算的时间不确定性（charts 环境，新模块 `calculations/bazi/time_basis.py`）

1. `resolve_birth_instants(date, reported_time, place, clock_basis) -> list[Instant]`：
   - 用 `zoneinfo` 与 tzdata 解析当地规则（中国大陆用 `Asia/Shanghai`；港澳台和海外按出生地时区）。两个锁文件都锁定 `tzdata` 包，保证 Windows 与 Linux 结果一致。
   - 日期落在夏令时期间、且 `clock_basis=unknown` 时，生成"按钟表时间（需减 1 小时）"与"已是标准时"两个分支，并要求用户确认（§G 话术）。
   - 落在重复时刻时生成两个分支；落在不存在的时刻时标 `nonexistent`，提示用户核对。
   - 1949 年前（如 1940 年代上海夏令时）同样以 tzdata 为准，并标"历史时区数据可能有误差"。
2. `solar_time(instant, lon) -> {standard, mean_solar, true_solar, eot_minutes}`：
   - 真太阳时 = 标准时 + (经度 − 时区中央经线) × 4 分钟/度 + 均时差。
   - 均时差用公开的天文算法（NOAA 或 Meeus），方法名写进输出。
   - 测试：取 6 个日期（含 2 月中旬与 11 月初两个极值附近）与 NOAA 太阳计算器的公开数值对照，误差 ≤0.5 分钟，对照表写进 `docs/v4/evidence/P8/time-basis-crosscheck.md`。
3. **口径**：
   - 输出同时给出"标准时口径"和"真太阳时口径"的时辰、晚子时口径下的日柱，以及距节气交接 ±2 分钟内的"节界不确定"标记（14 号 H.6）。
   - 默认用哪个口径做解读，是流派选择，**要问用户**（见文末）；用户回答前，两种口径一致时直接用，不一致时作为两个候选分支并列。
4. 候选集合：所有 Instant × 口径 → 去重后的（时柱、日柱、月柱）组合；`precision=unknown` 时，再加上 12 个时辰（每个时辰取中点，并在交界前后各取一个采样点，沿用 U9 原意）。
   - 复用 `ChartAdapter._branches` 与 `_stability`。
   - `TimeBranch.input_precision` 新增枚举值 `rectified`（`domain/calculation.py:73`），并写迁移说明与兼容测试。
5. 所有候选的时柱都相同时，结论为"时柱稳定，无需校正"，流程结束。

### E. L3 大事吻合度（项目口径 `rectification_rules v1`）

- 规则表 `knowledge/rectification_rules_v1.json`：

      {event_type: [{signal, system, layer: 大运|流年, weight, source{book, chapter}|null, note}]}

  - `signal` 引用 U2 时间交互表的关系类型，或 U12 规则命中的 `rule_id`，例如婚姻 → 流年合动夫妻宫/配偶星；搬迁 → 冲动驿马或日支被冲。
  - 每个映射都标【传统说法】与出处，找不到出处的写 `source: null, note: "项目口径，待审"`。
  - 权重为项目口径 v1。
- 紫微：各候选的流年命宫与流年四化落宫，作为**单独一列**，不与八字分数相加（v1 不做跨体系加权）。
- 预计算：对每个候选，计算出生后 6 岁至今每一年的信号向量（年份 × 候选 × 信号）。之后的评分、留出、置换都是查表运算，保证 1000 次置换在 charts 进程内 10 秒内完成（给出测量）。
- 每个候选输出逐事件的"支持/不支持"证据条目，带 `〔c#〕`/`〔r#〕`。

### F. 防过拟合（全部在代码中强制执行，模型无法绕过）

1. **冻结**：用户确认事件清单后计算 `events_hash`（规范化 JSON 的 sha256），记录 `rules_version`，状态转为 `frozen`。冻结后：
   - 新增的事件写 `added_in_round=2`，不进入第 1 轮结果；
   - 不允许修改已冻结事件的年份（只能整条作废，作废也会被记录）。
2. **留出验证**：事件 ≥6 件时，按 `hash(session_id)` 固定随机种子，留出约 1/3。用其余事件确定领先候选，再看领先候选在留出事件上的排名。项目口径：排名前 2 记为"留出支持"。事件 <6 件时不做留出，结论最多为"弱倾向"，而且必须说明。
3. **置换零假设**：
   - 每件事在其类型的合理年龄区间内随机换一个年份（区间表为项目口径，例如升学 6–30 岁、结婚 18–60 岁、生子 18–50 岁，写进规则表）；
   - 重复 1000 次，计算每次的"最佳候选得分"；
   - `p = (1 + 零分布中 ≥ 实际得分的次数) / 1001`。
4. **可区分的条件**：同时满足 `p ≤ α`（第 1 轮 α=0.05，第 2 轮 α=0.025）、留出支持、领先幅度 ≥ δ。
   - δ 由 §J 的 E-R2 标定：取使"零数据集上报'可区分'的比例 ≤5%"的最小 δ。
   - 否则结论为"分不出来"。
5. **最多两轮**：第 2 轮的问题由程序选择，选的是"候选之间分歧最大的年龄段"（不点名事件类型）；第 2 轮用全部事件重新检验，α=0.025。

### G. 防确认偏误（流程与提示词）

- 新叠加提示词 `prompts/rectification.md` v1.0.0（逐字使用，与 crisis/onboarding 一样叠加在 system 之后；流程期间叠加）：

```markdown
<!-- prompt: rectification v1.0.0 -->
# 现在在帮他校正出生时辰
你的任务是帮他把关于出生时辰的证据整理清楚，而不是"算出"一个时辰。按这个顺序来，每轮只问一件事：
1. 先问有没有出生证明、医院记录，或者家里谁记得出生时间、记得多清楚。有可靠记录的，就以记录为准，后面只需要核对夏令时和真太阳时。
2. 确认出生地（城市即可），以及这个时间是不是当时钟表上的时间。
3. 收集人生大事：只问"哪一年发生了什么、记得多确定"。不要提任何时辰、时柱或候选，也不要问"那年是不是有变动"这种带方向的问题。
4. 大事列好后，请他确认清单。确认后清单就冻结，之后补充的事会单独记一轮。
5. 结果出来后，如实转述程序的结论：
   - 程序说"可以区分"时，说"更倾向 X，这是推断，不是确认"，讲清支持和不支持的证据；
   - 程序说"分不出来"时，就说命理吻合度分不出这些候选，并告诉他哪些结论不受时辰影响、哪些会受影响；
   - 可以提一句：独立研究发现，靠人生大事反推时辰通常分不出来，最可靠的仍是出生记录和家人的回忆。只说一次，不要说教。
6. 采不采用某个时辰由他决定；他确认后才会改资料。
不要自己推算夏令时、真太阳时或任何盘面数据，一律以工具结果为准。
```

## 测试

- `time_basis`：
  - 夏令时：1986、1988、1991 年的开始日、结束日、重复时刻、不存在时刻；
  - 1940 年代上海；
  - 香港、台湾的样例各一；
  - 真太阳时的 NOAA 对照（≤0.5 分钟）；
  - Windows 与 Linux 在 CI 上结果一致。
- 规则表 schema 校验；预计算与置换的性能测量；冻结哈希的稳定性；第 2 轮 α 的计算。
- 结构检查："收集中禁提时辰"的正反例各 ≥15。
- 撤销传播：事实撤销后，结果标"依据已变化"。
- 场景：19 号的 RT01–RT09 脚本模式 100%；RT10（E-R2 假阳性）作为离线评测任务通过门槛。

## 验收标准（可观察）

1. 输入 1988-07-15 09:30、成都、"不确定是不是钟表时间"：工作台列出"钟表时间 → 标准时 08:30 → 辰时"和"已是标准时 → 巳时"两个分支，并用一句话问用户确认，不直接下结论（RT01）。
2. 输入乌鲁木齐 1995-03-10 09:40：结果同时显示标准时口径（巳时）与真太阳时口径（辰时），各自标明口径（RT03）。
3. 用户说有出生医学证明写着 08:20：不进入大事评分，结果为"以记录为准"，只做换算核对（RT04）。
4. 用随机事件的合成人物跑完整流程：结论为"分不出来"，回答中没有"更倾向"，并分开说明稳定结论与受时辰影响的结论（RT05）。
5. 冻结后补充一件事：第 1 轮结论不变，新事件显示为"第 2 轮"（RT06）。
6. 收集阶段的回答里没有任何时辰名（RT07 硬断言）。
7. E-R2 零数据假阳性 ≤5%（附 Wilson 区间）；E-R1 ≥95%；报告开头有指定的声明句。
8. 用户确认前，出生资料没有任何变化（数据库断言）；确认后 `precision=rectified`，档案中记录了校正记录 id（RT08）。
9. ExecPlan 与阶段回执。

## 何时停下来问用户 / 大脑

- **默认口径**：解读默认用北京标准时还是真太阳时（流派选择）？请用户决定；回答前两种口径不一致时并列。
- **E-R3**：是否下载并在本机使用 AstroDatabank 公开资料（需用户批准下载，并说明来源与大小）。
- E-R2 无论 δ 取多少，零数据假阳性都 >5%：停下来报告大脑，不要放宽检验。
- `rectification_rules v1` 的事件类型 → 信号映射写完后：交用户抽查，用户可能有流派偏好；抽查前可以先用于合成评测。
- 交叉核对发现现有 v3 计算与 tzdata 换算不一致（例如有地方写死了 UTC+8）：**立即报告**，不自行修改旧口径（沿用原 P8 规则）。
