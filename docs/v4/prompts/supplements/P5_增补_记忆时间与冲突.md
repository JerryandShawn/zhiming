## 背景（证据）

- MemoryAgentBench（arXiv 2507.05257）中，"先植入事实、再给更正"的冲突题是所有系统最弱的一项：多跳 ≤7%；商用记忆层单跳只有 7%（Zep）至 18%（Mem0）。
- Zep/Graphiti（arXiv 2501.13956）用双时间模型（事实有效期 + 系统写入时刻），矛盾时设旧事实的失效时间而不删除，时间推理与跨会话推理都有明显提升；但"助手在会话中说过的话"这类题从 94.6% 降到 80.4%，说明只存抽取出的用户事实会丢掉助手自己的建议。
- LongMemEval（ICLR 2025）：按"轮"切分检索单元最好；时间感知检索提升时间推理召回 6.8–11.3 个百分点。
- 同一张八字盘，不同模型（甚至同一模型多次推理）可能得出不同格局（BaZi-LLM 案例：伤官格与从儿格）。档案需要记录判断"稳不稳"。

## 设计要求

### A. 双时间事实与同槽更新（`memory/policy.py`、`memory/slots.py`（新增）、`memory_write`）

1. **fact 新增字段**（JSON 内，不改表结构）：`slot`（可空）、`valid_from`（默认 `said_at`）、`valid_to`（可空）、`superseded_by`（可空）、`supersedes`（可空）。
2. **槽位表** `memory/slots.py`：≤30 个常用槽位，每个槽位写清 `cardinality`（`single` 只能有一个当前值 / `multi` 可并存）与识别线索。至少包括：

   | 槽位 | cardinality | 例子 |
   | --- | --- | --- |
   | 居住城市 | single | "搬到上海了" |
   | 工作单位 | single | "入职了 B 公司" |
   | 职业/岗位 | single | — |
   | 感情状态 | single | — |
   | 饮食偏好·辣 | single | "最近能吃点辣了" |
   | 作息 | single | — |
   | 备考目标 | single | — |
   | 称呼 | single | — |
   | 重要的人·X | multi | — |
   | 爱好 | multi | — |

   槽位由模型在 `memory_write` 的新可选参数 `slot` 中给出，代码按槽位表校验（未知槽位视为不填）。
3. **写入时的冲突处理**（代码完成）：
   - 同一 subject、同一 `single` 槽位已有有效事实，且新事实的 `said_at` 更晚：
     - 旧事实 `valid_to = 新事实.said_at`、`superseded_by = 新事实 id`，`status` 保持 active（历史可查），但检索与 L2 视为无效（`valid=false`）；
     - 新事实写 `supersedes`；
     - 回执 `write_status = updated`，摘要例如"已更新：工作城市 杭州 → 上海"，带 `undo_token`。
   - 新事实没有给出槽位，但与已有事实在检索上高度相似且语义可能相反（向量相似度 ≥ 阈值，阈值为项目口径，测试中固定）：返回 `possible_conflict{fact_id, summary}`，**不自动覆盖**；模型据此温和确认（`ask_user` 的 `slot` 写对应槽位）。
   - 敏感类槽位（健康、他人隐私、金额等）仍按原 §A 先生成 proposal；proposal 确认后才执行上面的覆盖。
   - "临时状态"不覆盖长期槽位："在上海出差一周"不能取代"居住城市"。槽位表的识别线索要写出这类反例，测试覆盖。
4. **撤销**：撤销"更新"时，新事实 retired，旧事实的 `valid_to` 与 `superseded_by` 恢复为空（复用 `retire_fact`，`memory.py:298-325`，并通过 `mutation()` 幂等）。
5. **遗忘传播**：被 `memory_forget` 的事实如果在 `superseded_by` 链上，链两端都要正确处理：删除新值时旧值恢复有效；删除旧值时新值的 `supersedes` 置空。写测试。
6. **画像（L2）与 `<相关记忆>`（L4）**只展示 `valid=true` 的当前值；L4 若检索到旧值，以 `valid:false` 标出（P3 增补 §C 的 JSON 行格式）。

### B. 助手话语检索单元（`memory/retrieval.py`、`agent/envelope.py` 的 finalize）

1. **按"轮"索引**：每个"用户消息 + 紧随其后的助手消息"组成一个检索单元 `round`（新的检索粒度，不是新的实体种类）：写入 `search_tokens` 与向量，引用别名 `〔m#〕` 指向助手消息。
2. **`assistant_claim` 条目**：finalize 时，若本轮回答满足以下任一条，生成一条 `note`，字段为 `origin=assistant_claim`、`inferred=true`、`source_ids=[助手消息 id]`：
   - 调用了 `present_options`；
   - 引用了 `〔c#〕` / `〔r#〕` 并给出命理判断；
   - 含"建议你……"类明确建议。

   内容是一句话摘要："明镜建议面试前做三件事：……"。
   - 这类条目**永远不能成为用户事实**（蓝图 §16 不变量 3），模型只能说"我上次说过……"。
   - 结构检查（P6）对"你说过"指向 `assistant_claim` 的情况告警（`memory_error`）。
3. **遗忘传播**：助手消息被脱敏或删除时，对应的 `round` 索引与 `assistant_claim` 一并删除。

### C. 时间过滤进入检索实现（`memory/retrieval.py`）

- `search(owner, subject, query_tokens, kinds, limit, since, until)`（P2）支持按 `event_at` **或** `said_at` 落在区间内过滤：事件类按 `event_at`，其他按 `said_at`。
- 向量检索与全文检索都应用同一过滤；融合打分（0.6·向量 + 0.4·全文）之后，对时间命中项加权（权重为项目口径，写进配置）。
- P3 增补 §B 的 `parse_time_range` 是唯一的时间解析入口，本阶段不再另写。

### D. 命理档案的稳定度（`chart_interpretation`，与 P8 增补 U15 对接）

- 每项核心判断（格局候选、旺衰、喜用）新增：
  - `stability: stable｜leaning｜uncertain`：3 次独立推理中 3/3 一致为 stable，2/3 为 leaning，否则为 uncertain；
  - `samples`：每次推理的结论，以及引用的 `〔c#〕` / `〔r#〕`；
  - `method_version`。
- 生成逻辑在 P8；本阶段只提供实体、读写 API、版本历史，以及进入画像第 7 节的摘要格式（例如"喜用候选：木（扶抑，倾向）；火（调候，稳定）"）。

## 测试

- 槽位与冲突：
  - 每个 `single` 槽位都有"更新"正例；
  - "临时状态"反例 ≥8 条；
  - 撤销更新后旧值恢复；
  - 遗忘链两端的处理。
- 助手话语：`round` 单元在第 50 轮之后仍能召回第 1 轮助手的建议（AS01）；`assistant_claim` 不进入 facts（数据库断言）。
- 时间过滤：TR01–TR03 在向量开启和关闭两种配置下都通过。
- 脚本模式：19 号的 KU03–KU06、AS01–AS02、TR01–TR03，加上原 P5 场景，全部 100%。
- 实测：记忆类场景（M、R、KU、AS、TR）合计 ≥85%。日期、名称、城市等保持**硬断言**，评审只评语气与完整性（宽松评审会抬高记忆分，见 17 号 §3.1 LoCoMo 审计）。

## 验收标准（可观察）

1. 先说"我在杭州工作"，一周后说"我搬到上海了"：回执显示"已更新：杭州 → 上海 [撤销]"，之后问"我在哪工作"只答上海（KU01、KU03）；点撤销后再问，答杭州（KU04）。
2. 说"我下周在上海出差"：居住城市不被覆盖（KU05）。
3. 50 轮之后问"你上次建议我面试前做什么？"，回答复述当时的建议，并带 `〔m#〕` 引用（AS01）。
4. 用户把明镜的判断说成自己说过的（"我上次说我喜用是木对吧"）时，回答更正："那是我上次的判断，不是你告诉我的"（AS02）。
5. 数据库中 `assistant_claim` 条目数 > 0，且 facts 中 `origin` 为助手的数量为 0。
6. 原 P5 的全部验收标准照旧；迁移文件名为 `0009_memory_proactive.sql`。
