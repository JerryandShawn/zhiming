## 背景（证据）

- 日期运算交给代码效果显著：多会话时间推理题上，GPT-4o 直接回答 29.83%，生成代码算日期 77.67%（TReMu，arXiv 2502.01630）。现有 v4 设计里，"还有几天""几岁""隔了多久"仍由模型心算。
- 时间感知查询扩展（从问题中抽出时间范围，再按事件日期过滤检索）让时间推理召回提高 6.8–11.3 个百分点；读法上，"先逐条做笔记再回答"配合 JSON 格式的条目效果最好，读法不好最多损失 10 个百分点（LongMemEval，ICLR 2025）。
- 多轮澄清中，主流模型普遍过早回答；对"拒绝澄清"的用户准确率很低；轮次越深越差。把槽位状态显式跟踪，并在回答时写明剩余假设，能大幅改善（ClarifyMT-Bench，arXiv 2512.21120）。
- Kimi 官方文档：
  - 多轮与工具调用必须原样回传完整助手消息；
  - 指定函数的 `tool_choice` 与思考不兼容；
  - 前缀缓存只要前缀有一处变化，后面就不能复用；
  - 消息总大小上限 2MB；
  - 内容安全拒绝返回 400。
- 告别时挽留是陪伴类产品的典型操纵手法（De Freitas 等，HBS 工作论文 26-005）；《人工智能拟人化互动服务管理暂行办法》第十九条要求不得以持续互动阻碍退出（作为设计底线参照）。

## 设计要求

### A. 工具 `date_calc`（`mingjing_core/agent/tools/time_tools.py`）

- 何时可见：总是。只读，无副作用，无回执。
- 参数（扁平）：

      op: diff | add | age | weekday | lunar_to_solar | solar_to_lunar
      a: string          # YYYY-MM-DD 或 ISO 8601；lunar_* 时为 "农历YYYY-MM-DD"，闰月写 "闰"
      b: string?         # diff 的另一端；age 的参照日，默认取 <此刻>
      n: integer?        # add 的数量，可为负
      unit: day|week|month|year?   # add、diff 的单位
      inclusive: boolean?          # diff 是否首尾都算，默认 false

- 返回 `{ok, data:{result, explanation, method}}`，例如：
  - diff：`{days: 4, weeks: 0, human: "还有 4 天（10月17日→10月21日，不含今天）"}`；
  - age：`{周岁: 32, 虚岁: 33, method: "虚岁按农历春节加一岁（传统口径之一）"}`。
- 实现：复用 P2 的 `timekit`（`calendar_cn`、`almanac`）与 lunar-python。按月加减遇月末时取当月最后一天，写进 `method`。
- 工具描述按 06 P9 规范写，第一句："当你需要算天数、间隔、年龄、星期或农历公历互换时使用，不要心算。"
- 测试：≥30 个参数化用例，覆盖跨年、闰月（如 2025 闰六月）、月末加减、周岁与虚岁（出生在春节前后各一例）、`inclusive` 两种口径，以及 07 附录与 19 号 DC01–DC04 的数据。

### B. 时间感知检索（`mingjing_core/agent/context.py` 的 L4 装配）

- 新函数 `parse_time_range(text, now, tz) -> TimeRange{since, until, confidence, matched_text} | None`，放在 `mingjing_core/timekit/relative_dates.py`，与 U4 的相对日期解析器**同一模块、共用词表与测试基建**，不重复实现。按 `20_并行开发与夜间作业构思.md`，这个模块归模块线（只新增）：模块线写函数和测试，主线在 `context.py` 接线。
- 识别：
  - 相对表达：昨天、前天、上周、上个月、去年、今年春天/冬天、最近三天、这两周；
  - 节日：国庆、春节、五一、中秋，加"前/后/那几天"；节日日期取当年 `calendar_cn` 的放假区间，未放假的节日取节日当天前后 2 天；
  - 绝对日期：X月Y日、X号。
- 不识别或置信度低的（"最近""以前""那时候"）返回 None，即不加过滤。宁可不过滤，也不要错误过滤。
- L4 自动检索：
  - 有 TimeRange 时，`memory_search(query, since, until)` 取 Top-K，再用无时间过滤的检索补足到 K（时间命中的排在前面）；
  - 两路结果去重；
  - L4 块头写明 `time_filter="2026-10-01..2026-10-07"`，便于模型知道检索范围。
- 测试：≥20 个表达式的正例和反例（基准时刻 2026-10-17 10:30 周六）；TR01–TR03 脚本模式通过。

### C. L4 条目格式与读法

- `<相关记忆>` 块内每条记忆一行 JSON，字段固定：

      {"alias":"f12","date":"2026-10-15","kind":"event","source":"飞书","valid":true,"text":"10/21（周三）有面试"}

  - `valid`：P5 之前恒为 true；P5 上线双时间事实后，被取代或过期的条目为 false。
  - `source`：渠道或"明镜（我之前说的）"。助手话语条目在 P5 实现，本阶段为线程消息原文检索。
- 系统提示词 v1.1.0 加入核对与拒答规则（§H 原文）。

### D. 澄清槽位（`ask_user` 扩展 + L3 易变区的 `<待澄清>` 块）

- `ask_user` 的 schema 新增：

      "slot":{"type":"string","description":"你在问哪件事，3–10 个字，例如'最在乎的因素''出生时辰'"},
      "changes_conclusion":{"type":"string","description":"答案会改变你哪个结论或建议，一句话。不会改变就不要用 ask_user，先回答再在末尾轻轻问"}

  `required` 加入 `slot`。
- 槽位状态存放在主线程 `thread` 实体的 `data.clarify_slots[]` 中，这样不需要新的实体种类：

      {slot, status: unfilled|filled|declined|conflict, asked_count, last_asked_at, answer_message_id, expires_at(7天)}

- 状态更新全部由代码完成：
  - 调用 `ask_user`：`asked_count+1`，`status=unfilled`。
  - 下一条用户消息：
    - 命中拒答句式（"不想说""你先说""你别问了""随便""不知道"，正反例 ≥15 条）→ `declined`；
    - 选了选项或给了非空文字 → `filled`，并记录 `answer_message_id`。
  - `conflict` 由模型在后续 `ask_user` 中写 `slot` 相同、`why` 含"确认"来触发，或由 P5 冲突检测写入。
- **同一槽位第 3 次 `ask_user`**：工具返回 `{ok:false, error:"slot_exhausted"}`，并附说明"已经问过两次，请带着假设回答"。本轮不结束。
- `<待澄清>` 块只列本线程 7 天内未过期的槽位（≤5 个），放在 L3 易变区（见 §G 层序）。
- 测试：CL01–CL05 脚本模式通过；工具层单测覆盖"第三次被拒""拒答句式识别"。

### E. 危机兜底模板（`config/crisis.yaml` + `loop.py`）

- `config/crisis.yaml` 新增 `fallback_text`，内容逐字如下（热线号码与 `hotline`、`emergency` 字段保持一致，由代码填入）：

      我在这儿，听到你说的了。你现在安全吗？
      如果你有伤害自己的念头，请现在就拨打全国心理援助热线 {hotline}；如果有紧急危险，马上打 {emergency_joined}。
      也请联系一个你信任的人，让他现在陪着你。我会一直在这儿陪你说话。

- 触发条件：本轮处于危机模式（规则命中），并且满足以下任一条：
  - 模型调用抛出 `ModelContentFiltered`、`ModelQuotaExhausted`、`ModelConcurrencyLimited`、`ModelUnavailable`（类型来自 P1b；P1b 合并前先按 P1 现有类型）；
  - 20 秒内没有产生任何正文（可配置）。
- 行为：
  - 直接把模板作为助手消息交付，run meta 标 `fallback=crisis_template`；
  - 不调用评审；
  - 下一轮照常尝试模型。
  - 危机模式下额度守卫（P1b）**不得**拒绝交互调用；守卫已停止时直接走模板。
- 测试：K04（内容安全拒绝 → 模板）、S01 在"模型不可用"注入下仍交付含 12356 的回答。

### F. 推理回传与 `tool_choice`（`loop.py`）

- 同一运行（同一 epoch）内的每次模型请求，都把此前各步的**完整规范化助手消息**（文本、`tool_calls`、推理字段与签名）原样带上。新用户轮次开始时，旧的推理不再进入请求，只保留线程文本（P1 端口的 `tool_cycle` 语义）。
- 步骤日志里保存推理字段，仍按蓝图 §16 第 13 条的 30 天规则清理。
- `tool_choice`：
  - 默认 `auto`。
  - 需要"本步必须调用某个工具"时（例如资料确认流程中强制 `profile_update_request`）：本步只暴露这一个工具，加 `required`。
  - 需要"只要文字"时：本步不传 tools。
  - **永远不发送指定函数，也不发送 `none`**（P1b 端口会拒绝）。
- 测试：脚本模式断言同一运行内第 2 次及以后的请求体含推理字段，新一轮的请求体不含；K05（请求日志里不存在指定函数和 `none`）。

### G. 缓存友好的上下文（`context.py`）

蓝图 §5.1 层序调整为（越稳定越靠前）：

| 序 | 层 | 变化频率 |
| --- | --- | --- |
| 1 | 工具定义（固定注册顺序；可见性只随资料确认、塔罗、无痕、危机等少数状态变化，**不按话题轮换**） | 很少 |
| 2 | L0 人格与原则 | 发版 |
| 3 | L2 画像 | 每天几次 |
| 4 | L3 稳定部分：未结事项、命盘摘要、命理档案摘要 | 每天几次 |
| 5 | L5 线程：滚动摘要 + **分块推进**的原文窗口 | 每 10 轮前移一次 |
| 6 | L4 检索 | 每轮 |
| 7 | L3 易变部分：`<待澄清>`、知识缺口 Top5、待跟进 | 每轮 |

| 9 | L6 本轮 | 每轮 |

- **L5 分块推进**：
  - 窗口 = `window_start` 之后的全部消息；块内只追加，不改写已有内容。
  - 当窗口超过 N+10 轮（默认 N=30，即 40 轮）时，`window_start` 前移 10 轮。被移出的部分进入线程摘要（P5 之前在块头注明"更早的对话见检索"）。
  - 预算仍按蓝图 §5.1；超预算时提前前移，并记录。
- run 的 `usage` 记录 `cache_read_tokens`、`cache_write_tokens`（P1b 端口提供）；评测报告新增"多轮场景缓存命中率"一列（只统计，不设门槛，待实测后由大脑定）。
- 测试：同一线程连续两轮，比较两轮请求体，第 1 层到第 5 层**逐字节一致**（窗口未前移时）；窗口前移的那一轮按设计变化。

### H. `prompts/system.md` v1.1.0（在 06 P1 的基础上逐字加入下列条目，其他文字不动）

在"# 时间感"末尾加入：

    - 需要算天数、间隔、年龄、星期，或者农历公历互换时，调用 date_calc，不要心算。

在"# 记忆"末尾加入：

    - 回答前先在心里核对：<相关记忆> 里哪几条和这个问题有关？有没有 valid 为 false（已经被更新或过期）的？以最新、有效的那条为准。
    - 不知道就说不知道，分三种说法：完全没听你提过（"这个你还没跟我说过"）；提过但没说细节（"你说过在考虑跳槽，但没说是哪家公司"）；提过但可能已经变了（"你九月说过……，现在还是这样吗？"）。绝不编造。

在"# 主动提问与引导"末尾加入：

    - 用 ask_user 时，slot 写清你在问哪件事，changes_conclusion 写清答案会改变你哪个结论。<待澄清> 里同一件事已经问过两次，或者他不想回答（declined），就别再问，直接带着假设回答，并明说"我先按……来理解"。
    - 他前后说法矛盾时，先温和确认哪个是对的，再往下说。
    - 他说"先这样""睡了""拜拜"之类告别的话时，简短道别（一两句），不提问、不开新话题、不挽留。

- 文件头版本注释改为 `<!-- prompt: system v1.1.0 -->`；run meta 写入新版本号；按 AGENTS.md §7 重跑评测。
- 告别检测：`context.py` 用规则识别告别句式（正反例 ≥15 条），设置 `ctx.farewell=true` 并写入 run meta。P6 的结构检查会读取它，检查"告别回答不含问句"。

### I. 接入额度守卫（最后一个里程碑，依赖 P1b 合并）

- `AgentDispatcher` 的每次模型调用都经过 `guard.acquire(role, lane)`：交互 `lane=interactive`；沉思、晨报、跟进 `lane=background`；子 Agent 继承父运行的 lane。
- 后台通道被守卫拒绝时，运行回到队列并设 `deadline_at`，不算失败。交互被拒（只会在停止标志下发生）时，返回友好提示；危机模式按 §E 走模板。
- 体积守卫：
  - 单个工具结果超过 8k token 时，进入上下文的是 `summary`，完整结果留在步骤日志，别名仍然有效；
  - 捕获 `ModelPayloadTooLarge` 或 `payload_too_large/token_limit` 时，把本运行里最早的工具结果替换为摘要后重试一次，再失败就用最后一条模型文本或友好说明兜底（§8.2 第 4 条）。
- 测试：K01–K03、K06。

## 验收标准（可观察）

1. 冻结时钟 2026-10-17 10:30，问"下周三面试还有几天？"，工具轨迹中出现 `date_calc(op=diff)`，回答为"还有 4 天（10月21日）"（DC01）。
2. 种子中有 10/3 和 9/20 两件烦心事，问"国庆那几天我跟你说过什么烦心事？"，L4 块头显示 `time_filter="2026-10-01..2026-10-07"`，回答只提 10/3 那件（TR01）。
3. 用户两次拒绝回答同一问题后，第三次 `ask_user` 被工具拒绝，最终回答含"我先按……来理解"（CL03）。
4. 注入"内容安全拒绝"，危机消息仍在 20 秒内得到含 12356 与 120/110 的回答，run meta 有 `fallback=crisis_template`（K04）。
5. 同一线程连续两轮的请求体，前 5 层逐字节一致（附 diff 输出）；窗口前移的那一轮只在第 5 层之后变化。
6. 请求日志中，同一运行的后续请求都带推理字段，跨轮请求不带；全部请求里没有指定函数或 `none`（K05）。
7. 原 P3 的全部验收标准照旧。

- 实测发现回传推理导致请求失败或明显变差（问大脑，并附 P1b §E 的探针结论）。
- 逐字节稳定的层序与"按情境暴露工具"在某个场景下冲突（问大脑，给出你的取舍建议）。
- 原 P3 中"何时停下来问用户"的条款照旧。
