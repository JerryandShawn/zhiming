- v3 校验器 `application/consultation.py:527-926`：约 400 行、134 次正则调用、13 类问题；大量针对具体转录的补丁（如 `:706-713` 的 `re.fullmatch(r'(?:今天)?向A发出班次与', start)`、`:794-811` 的整句白名单）。
- 失败处理 `:928-939`：只修一次，仍有问题抛 `InvalidAnswer`，`runtime/graph.py:42-44` 把它换成"本轮阶段未完成"——**用户拿不到任何回答**。
- 69 个 `tests/test_core_*.py` 中约 29 个是否定句回归（文件名含 4288、5908、8A7 等），`tests/fixtures/*.json` 存有对应转录。
- `docs/CORE_V3_BEHAVIOR_COVERAGE.json` 记录 102 项旧行为映射，`tests/test_core_architecture.py` 会核对它。

## 目标

1. **永不吞答案**：任何校验问题都不能让用户拿不到回答。
2. 硬约束由工具层保证（P3 已做），本阶段补齐**结构检查**（§8.2）。
3. **评审员**（§8.3）：与主模型相同的模型、**完全独立的上下文**，对照证据按 rubric 复核；严重问题触发一次修订，前端显示"已修订"。
4. 旧正则**原样**迁为 `legacy_lint`，只告警；旧回归测试改为 lint 语料测试。
5. 危机支持模式的完整实现与 100% 测试。

## 设计要求

### A. `mingjing_core/validation/legacy_lint.py`
- 把 `consultation.py:527-926` 的逻辑**原样搬迁**（允许为可读性拆函数，但规则与正则文本不变），接口改为 `lint(text, context) -> list[Finding{rule, severity(1-5), span, message}]`，永不抛异常（内部异常 → 一条 `lint_internal_error` finding）。
- v3 运行路径保持旧行为（v3 仍调用旧 `_validate` 并 fail-closed，直到 P11 退役——现网 v3 的行为不在本阶段改变）；v4 运行在 finalize 后调用 `lint`，结果写 run meta `review.lint[]` 与指标，**不影响交付**。

### B. `mingjing_core/validation/structural.py`
- 实现 §8.2 的四条：未知别名移除并记录；无 `saved` 回执却声称已保存 → 在该句后附注（附注文字：`（这条还没有真正保存，需要的话告诉我）`）；`ask_user` 每轮最多一次（多余的调用在工具层拒绝）；空回答兜底。
- 声称已保存的检测用一个**小而清晰**的模式集（≤ 10 条）+ 否定识别（"没有记/不会记/还没保存"不算声称），正反例各 ≥ 15 条。不要再造一个 134 条的怪物。

### C. `mingjing_core/validation/critic.py`
- 角色 `critic`（`config/models.yaml`）。**用户决定**：与主模型相同，生产默认用 `k3-256k` 以节省会员额度，上下文完全独立：
  - 每次复核都新开一次调用，只传下面列出的材料，**禁止**传入主运行的消息列表、系统提示、推理字段或工具轨迹；
  - 用测试证明评审请求的消息体里不含这些内容；
  - 评审遇到额度错误（`ModelQuotaExhausted`）时跳过复核，照常交付并记录；
  - 上线前用 P1 建立的 20 条人工校准集验证，一致率 ≥ 80%。
  - 提示词 `prompts/critic.md`（逐字来自 06 P4）；输入：用户本轮消息、此刻块、本轮使用过的记忆与声明摘要（别名+一句话）、回执列表、最终回答。
- 输出 JSON 校验（P1 的 schema 扁平化 + Pydantic）；解析失败重试一次，再失败视为 `pass` 并记录。
- `revise` 且存在 severity ≥ 3：主模型在同一运行内追加一次迭代，输入 issues，要求"只修正这些问题，保持其他内容"；新文本通过 `text_reset{reason:"revised"}` 推送；信封 `review={verdict, issues[], revised:true}`。**最多修订一次**；修订后不再评审（避免循环），但修订稿再跑一次结构检查。
- 评审员超时（默认 30 秒）或不可用 → 直接交付并记录。
- 用户不在乎 token：默认每轮都评审；owner 设置 `review_mode: always|deep_only|off` 可调（默认 always）。
- 流式时序：主回答先流式给用户；评审在 `finalize` 中进行；前端在评审期间显示一个不打扰的"复核中"小标记（P10 实现 UI），修订后替换。
