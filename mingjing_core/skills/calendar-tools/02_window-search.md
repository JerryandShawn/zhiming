# 择日与区间搜索：看清加减分，再自己选

版本：p8-skills-draft-2026-10-21-v2.3；只解释实际区间计算，不代替现实决策。

## 方法步骤

1. 用户要比较日子时，先明确起止日期、时区和用途。签约、面试、搬家、出行、表白、开业按具名用途调用window_search，不猜一个未确认用途。
2. 展示少量候选及每个候选的加分、减分、权重、净分和同分排序；用户可据自己的现实安排选更靠后的日期。
3. 把象征结构与现实门槛分开。面试看招聘方档期，签约看条款与审阅，搬家出行看天气交通，表白看关系和对方意愿，开业看准备和成本。

## 需要的盘面字段

根对象：P8ToolEvidenceResult。必读 `/version`、`/data`、`/rule_hits`、`/aliases`、`/sources`、`/effects`。
读取实际候选日期、用途、贡献清单、分数与排序说明；没有工具结果不自编“某日更好”。
每个结论引用候选自身的依据；另一个结果里的c1不能直接沿用。

## 各流派观点与分歧

日历、干支关系、四化与相位来自不同具名方法；用途权重和综合排序是项目定义，不是古籍量化吉凶表。
分值只解释当前筛选规则，没有人群校准，也不是成功概率。未计算的通书条件、地理条件与时段限制不能说已排除。

## 适用前提

范围合法且有当前出生资料版本，候选计算完整。缺算的日子保留状态，不把缺失当0分后默默排到末尾。
只比较日期的结果不能推荐某个小时；也不因权重使某日排第一就催用户付款、辞职或冒险。

## 反例与常见误读

多个加分结构不代表没有减分；同分不代表两天现实条件相同。
医院预约、航班和对方明确拒绝不能被排名覆盖。用户已经订好的安排不因一个“冲”字被要求取消。

## 表达示例

“这几天里，第一天按咱们这版规则排得靠前；加分来自这两项〔c#〕〔r#〕，也有一项需要留意的张力〔c#〕〔r#〕。你要是第二天更从容，就把准备做足，没必要为排名硬改日程。”

示例仅说明格式。实际先从当前候选的真实命中中取rule_id，再读取对应aliases.r及关联c别名；正负贡献都要可追溯，不引用未命中的r。

## 对应的规则命中 rule_id 列表

读取当前window_search.rule_hits及候选贡献引用，保留规则版本、school和source。
本章不新增U12，也不把一种关系对六用途一律解释为加分或减分。
